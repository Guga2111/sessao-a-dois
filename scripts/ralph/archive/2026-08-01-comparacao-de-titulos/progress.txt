## Codebase Patterns
- Frontend-only feature (client/). No backend/endpoint changes — reuse GET /api/media/{movie|tv}/{tmdbId} (MediaDetails).
- Any code in client/ must go through the frontend-design skill before implementing (project rule in CLAUDE.md).
- Modal fetch pattern to mirror: MediaDetailModal.tsx / PendingDetailModal.tsx.
- Lint gotchas (client/CLAUDE.md): no synchronous setState directly in a useEffect body — wrap fetch-on-mount in setTimeout(..., 0) + `cancelled` flag; reset state on tab change via key={activeTab} remount of a subcomponent, not setState-in-effect.
- Comparison-mode state is local useState per screen — do NOT touch Zustand stores.
- Reads use Skeleton + useDelayedLoading, never spinners.
- shadcn/base-ui Dialog usage: pass showCloseButton={false} + roll a custom close Button with a Portuguese aria-label, and always render <DialogTitle className="sr-only"> (base-ui Dialog.Popup needs an accessible name). See TitleModal.tsx / ComparisonDialog.tsx.
- "Fetch on Nth selection, show a dialog" flow: give the dialog's content props a nullable type (`T | null`) and render a Skeleton-shaped placeholder when null, instead of building a second loading-only dialog. Drive `open` as `loading || allItemsReady`; on failure leave items null (dialog never opens) and show the error+retry next to the selection UI instead. See ComparisonDialog.tsx (US-003).
- Selection-mode on an existing card/list component: add new optional props (all default off) and route the single existing onClick through a ternary based on the mode flag — don't add a second onClick prop or fork the component. See MediaCard.tsx (US-003).
- IMPORTANT: the canonical Ralph working files for this project are `scripts/ralph/prd.json` / `scripts/ralph/progress.txt` (that's what `scripts/ralph/ralph.sh` reads via `$SCRIPT_DIR/prd.json` and what `scripts/ralph/CLAUDE.md`'s "same directory as this file" instruction points to). A prior iteration mistakenly wrote the live PRD/progress state to `.claude/skills/ralph/` (the *skill's own* directory, meant only as the ralph-skill's doc/template location) instead — this left `scripts/ralph/prd.json`/`progress.txt` empty while real commits (US-001, US-002) only updated `.claude/skills/ralph/`. Fixed 2026-08-01 by mirroring the correct state into `scripts/ralph/prd.json`/`progress.txt` and keeping both locations in sync going forward. Future iterations: update BOTH `scripts/ralph/` and `.claude/skills/ralph/` together until this duplication is deliberately cleaned up (e.g. by deleting the live files from `.claude/skills/ralph/` in a dedicated pass).

## 2026-08-01 - US-002
- Implemented shared-highlighting + higher-rating indicators in ComparisonDialog.tsx (client/src/components/ComparisonDialog.tsx), building on US-001's two-column layout.
- Added `sharedNames(a, b)` helper: case-insensitive name match between the two columns' genre lists / watch-provider name lists, returning a `Set<string>` of lowercased shared names, computed once in `ComparisonDialog` via `useMemo` (keyed on `left.genres`/`right.genres` and the mapped provider-name arrays) and passed down to both `ComparisonColumn`s as `sharedGenres`/`sharedProviders`.
- Added `higherSide(left, right)` helper: returns `"left" | "right" | null`, returning `null` whenever either value is `null` (so an absent rating never counts as "winning") or when the two values are equal (tie = no highlight). Used for both the Nota do Casal (`coupleRating`) and Nota TMDB (`voteAverage`) rows.
- Genre pills and watch-provider pills: shared items switch from the neutral pill style (`border-[rgba(255,255,255,.1)] bg-[rgba(255,255,255,.05)] text-[#d6d2c8]`) to the same gold pill treatment already used for the Filme/Série type badge (`border-[rgba(255,203,43,.25)] bg-[rgba(255,203,43,.12)] text-[#ffdd7a]`) — reused an existing token combo instead of inventing a new one. The watch-provider fallback dot (shown when a provider has no `logoUrl`) also switches color (gold when shared, `#a6a39a` gray otherwise) so the highlight reads correctly even without a logo.
- Rating rows: the winning column's value text turns `#ffcb2b` (from the default `#f6f4ec`/bold-white) and gets a small `ArrowUp` icon (`lucide-react`, `strokeWidth={3}`, `aria-hidden`) appended after the value — kept deliberately subtle per the AC's "indicador sutil" wording, no badge/pill/animation.
- `ComparisonColumn` now takes `side: "left" | "right"` plus the four comparison props (`sharedGenres`, `sharedProviders`, `coupleWinner`, `tmdbWinner`) and derives `isCoupleWinner`/`isTmdbWinner` by comparing `side` against the winner — same computed-once-in-parent, consumed-by-both-columns shape as the shared-name sets.
- Files changed: client/src/components/ComparisonDialog.tsx; scripts/ralph/prd.json, scripts/ralph/progress.txt, .claude/skills/ralph/prd.json, .claude/skills/ralph/progress.txt (also fixed the dual-location prd.json issue noted in Codebase Patterns above).
- Quality checks: `npm run typecheck` passes; `npx eslint src/components/ComparisonDialog.tsx` clean.
- **Learnings for future iterations:**
  - This story was pure enhancement of an already-established design system (US-001's gold/neutral pill tokens, existing rating-row layout) — frontend-design's guidance was to reuse those exact tokens for the "shared" state rather than invent a new highlight color, and keep the rating-winner indicator understated (text color + one small icon, not a badge/glow/animation).
  - "Ausente não conta como maior nem menor" was implemented as: if either side of a rating comparison is `null`, `higherSide` returns `null` and *neither* column gets the winner treatment — not "the non-null side automatically wins." Same `null`-safe rule applied to both Nota do Casal and Nota TMDB for consistency, even though the AC text only spelled it out for Nota do Casal (voteAverage is realistically always present from TMDB, but the type allows `null`).
  - Shared-name matching normalizes to lowercase for comparison but renders the *original* casing from each column's own `item.genres`/`item.watchProviders.name` — no cross-column name substitution, so e.g. "Ação" vs "ação" would both highlight but each column still displays its own original string.
  - No browser verification possible in this sandbox (same Chromium/Playwright gap as US-001) — manual verification still needed before merge.

## 2026-08-01 - US-003
- Added comparison-selection mode to HubScreen.tsx: a "Comparar" toolbar button (Columns2 icon, Tooltip with the spec'd message) toggles `compareMode`; while active it flips to "Cancelar" (X icon) and reuses the app's existing gold-tint active-button token (same as MediaCard's "Avaliar" pill) instead of inventing a new one.

- A fixed bottom-center floating chip (`bg-[#161513]/95` + `backdrop-blur`, matches the prototype's pill motif) shows "N/2 selecionados" + a clear-X (resets to 0/2 without leaving compare mode); Escape key and the toolbar "Cancelar" both call `exitCompareMode()` (leaves the mode entirely, clears selection/dialog state).
- Extended `ComparisonDialog.tsx` (US-001/002) so `left`/`right` accept `ComparisonItem | null` — passing `null` renders a new `ComparisonColumnSkeleton` (Skeleton blocks shaped like the real column: poster/title/ratings/genre pills/synopsis lines) instead of needing a second loading-only dialog component. HubScreen drives `open` as `compareLoading || (compareLeft && compareRight)`; on fetch failure it leaves both `null` (dialog never opens) and shows the error + a "Tentar novamente" retry inline in the floating chip, keeping the 2 selections intact.
- Fetch-on-2nd-selection uses the established `setTimeout(...,0)` + `cancelled` flag wrapper (lint gotcha) keyed on the `selectedForCompare` array; retry re-triggers the same effect by giving the array a new identity (`setSelectedForCompare(prev => [...prev])`) instead of duplicating the fetch logic in a second function.
- `coupleRating` for each `ComparisonItem` = average of the track's own `reviews[].rating` (non-null only), or `null` if none rated — same computation already used by `MediaCard`/`MediaDetailModal`, just reused inline in a new `buildComparisonItem(track)` helper (calls `GET /api/media/{mediaType}/{tmdbId}` for genres/watchProviders/overview/poster/voteAverage/title/year).

## 2026-08-01 - US-004
- Added the same compare-mode/ComparisonDialog flow from HubScreen (US-003) to MatchScreen.tsx, covering both the "Descobrir" (SearchTab) and "Sugestões" (SuggestionsTab) tabs.
- Extracted a shared `useCompareSelection<T>(buildItem, keyOf)` hook (module-scope in MatchScreen.tsx, not a new file — it's only used by this screen's two tabs) that owns `compareMode`/`selected`/`left`/`right`/`loading`/`error`, the Escape-key listener, and the "fetch both on 2nd selection" effect (same `setTimeout(...,0)` + `cancelled` wrapper as HubScreen's). Both tabs instantiate their own copy, so switching tabs — which already fully unmounts the previous tab's component and mounts the other, since `{cond && <TabA/>}` / `{cond && <TabB/>}` are different component types — resets compare state "for free", satisfying the "reset selection via remount on tab switch" AC without needing an explicit `key={activeTab}` (no state lives in the parent `MatchScreen` component, so there's nothing to remount there).
- Added two module-scope `ComparisonItem` builders instead of one, per the AC's distinction: `buildComparisonItemFromSearchResult(result: MediaSearchResult)` reuses the already-known title/year/overview/voteAverage/posterUrl from the search result and only fetches `MediaDetails` for `genres`/`watchProviders` (Search tab); `buildComparisonItemFromDetails(mediaType, tmdbId)` (aliased as `buildComparisonItemFromPending` for `PendingMatch`) does a full `MediaDetails` fetch since `PendingMatch` only has `tmdbId`/`mediaType`/`title`/`posterUrl` (Suggestions tab). Both always set `coupleRating: null`.
- Shared `CompareToggleButton` (Tooltip + pill button, same `COMPARE_TOOLTIP` text as HubScreen) and `CompareSelectionChip` (floating "N/2 selecionados" + clear-X + error/retry) subcomponents, reused by both tabs so the toolbar button/copy stays in sync without duplicating JSX.
- SearchTab: added the Comparar button next to "Filtros" in the existing toolbar row; result cards get the dashed/gold-selected border + order badge treatment (same visual language as `MediaCard.tsx`'s compare mode) via a ternary on the card's `onClick`, and the "Curtir" button is hidden while `compareMode` is active (mirrors `MediaCard`'s footer-CTA-hidden-during-compare pattern) — added `event.stopPropagation()` on the Curtir button's click so it doesn't double as a card click once compare mode is off again.
- SuggestionsTab needed a different UI for selection than HubScreen/SearchTab: it normally shows one Tinder-style swipe card at a time (`pendingQueue[0]`), which can't be used to pick 2 items. While `compareMode` is active it swaps to a grid of ALL `pendingQueue` items (poster + title + type badge, same dashed/gold-selected treatment) so both items can be selected; the swipe UI and its Reject/Like buttons are only rendered when `compareMode` is false. Added a small header row above the tab content with a "N sugestões pendentes" caption + the Comparar button, visible in both modes.
- Files changed: client/src/screens/MatchScreen.tsx; scripts/ralph/prd.json, scripts/ralph/progress.txt, .claude/skills/ralph/prd.json, .claude/skills/ralph/progress.txt.
- Quality checks: `npm run typecheck` passes clean; `npx eslint src/screens/MatchScreen.tsx` clean; `npm run lint` (repo-wide) shows only the same pre-existing failures already documented above (RatingRequestDialog.tsx, ReviewModal.tsx, WatchModal.tsx, ui/button.tsx) — none in MatchScreen.tsx. `npm run build` (`tsc -b`) shows the same pre-existing PendingDetailModal.tsx/MatchScreen.tsx Select-Slider-onChange errors documented in the US-003 entry (confirmed pre-existing, not caused by this story's changes — the two new `tsc -b`-only errors at the Select/Slider lines were already there before this story touched those lines).
- **Learnings for future iterations:**
  - When two sibling tab components are rendered via `{activeTab === "a" && <TabA/>}` / `{activeTab === "b" && <TabB/>}` (different component types, mutually exclusive), switching tabs already fully unmounts/remounts — any `useState` local to one of those tab components resets automatically on tab switch, with no `key` prop or extra plumbing needed. Only reach for the `key={changingValue}`-on-a-subcomponent trick (documented in client/CLAUDE.md) when the resettable state lives in a component that stays mounted across the change (e.g. a shared parent).
  - A "compare 2 items" flow doesn't have to reuse the exact same list/grid UI the screen already has for its primary interaction — SuggestionsTab's swipe-one-at-a-time UI has no way to see/pick a 2nd item, so compare mode there renders a completely different (grid) view of the same underlying data (`pendingQueue`) rather than trying to force the swipe metaphor to support multi-select.
  - No browser verification possible in this sandbox (same Chromium/Playwright gap noted in every prior US-00x entry) — manual verification of both tabs' compare flows (toolbar toggle, card/grid selection visuals, floating chip, dialog skeleton→data, tab-switch reset, error+retry) is still needed before merge.
