## Codebase Patterns
- `@ConfigurationProperties` classes in this codebase are plain `@Component` beans (no `@EnableConfigurationProperties`/`@ConfigurationPropertiesScan` registered anywhere) - component scan picks them up because they live under `com.app`.
- bucket4j 8.10.1 (`com.bucket4j:bucket4j-core`, Java package `io.github.bucket4j`) API used: `Bucket.builder().addLimit(Bandwidth.classic(capacity, Refill.intervally(capacity, window))).build()`, then `bucket.tryConsumeAndReturnRemaining(1)` -> `ConsumptionProbe.isConsumed()`/`getNanosToWaitForRefill()`. A record component accessor cannot share a zero-arg signature with a static factory method of the same name on that record (e.g. `record R(boolean allowed)` cannot also declare `static R allowed()`) - javac reports it as "invalid accessor method... must be public", which is misleading; rename the static factory instead.
- `@WebMvcTest(SomeController.class)` only loads the controller + explicitly `@Import`ed beans - any plain `@Component` a controller depends on (e.g. `ClientIpResolver`) must be added to the test's `@Import({...})` list or the context fails to wire it. EXCEPTION: a `@Component` that also implements `jakarta.servlet.Filter` (e.g. `RateLimitFilter`) IS auto-included by `@WebMvcTest`'s default slice scanning even without an explicit `@Import` - Filter beans are one of the types `@WebMvcTest` picks up by default (along with `@Controller`, `@ControllerAdvice`, `@JsonComponent`, `WebMvcConfigurer`). Its own constructor dependencies (`RateLimitService`, `RateLimitProperties`, `ClientIpResolver`) still need explicit `@Import` though, since those are plain `@Component`s, not Filters.
- Spring Boot 4.1 moved Jackson to **Jackson 3** (`tools.jackson.core:jackson-databind`, package `tools.jackson.databind.*`) as the framework-managed one; `com.fasterxml.jackson.databind.ObjectMapper` (Jackson 2, package `com.fasterxml.jackson.databind`) is only pulled in transitively at runtime scope by `jjwt-jackson` and is NOT on the compile classpath. Any new code that needs to inject the Spring-managed `ObjectMapper` bean (e.g. to hand-write a JSON body in a raw servlet `Filter`, outside Spring MVC's message converters) must import `tools.jackson.databind.ObjectMapper`, not the `com.fasterxml` one.
- In-memory rate-limit/cache services that key by arbitrary strings (IP, email, user id) should evict inactive entries via a `@Scheduled` sweep (app already has `@EnableScheduling` on `SessaoADoisApplication`) rather than relying on an external cache library - keeps the dependency footprint small for a single-instance 1 CPU / 512M deployment.
- `api/src/test/resources/application.properties` sets `app.rate-limit.enabled=false` by default (US-002) - since it REPLACES main's `application.properties` for every `@SpringBootTest`/`@WebMvcTest` context, and `RateLimitFilter` is auto-included in every `@WebMvcTest` slice (see point above), leaving rate limiting on by default would make unrelated test classes that call login/register repeatedly across many `@Test` methods in the same class (sharing one cached Spring context, hence one singleton `RateLimitService` bucket map, hence one `127.0.0.1` IP key) trip the low default caps (register 3/min, login 5/min) and get spurious 429s. Any test that needs rate limiting actually active (like `RateLimitFilterTest`) re-enables it locally via `@TestPropertySource(properties = "app.rate-limit.enabled=true")` plus small capacities/windows (e.g. `2` / `3s`) so exceed/release assertions run in seconds, not real default windows of 1 minute/1 hour.

## 2026-08-04 - US-002
- Implemented `RateLimitFilter` (com.app.security), applying the per-IP limits from `RateLimitProperties` (US-001) to `POST /api/auth/login`, `/api/auth/register`, `/api/auth/refresh` and `/api/couple/join`, registered as a real servlet filter via `SecurityConfig.rateLimitFilterRegistration` (`Ordered.HIGHEST_PRECEDENCE`, deliberately NOT disabled like `jwtFilterRegistration`) so a blocked request never reaches Spring Security/BCrypt/the DB.
  - Exceeding the limit returns 429 with a `Retry-After` header (seconds) and `{"message": "..."}` body in pt-BR, written directly via the Spring-managed `tools.jackson.databind.ObjectMapper` bean (Jackson 3 - see Codebase Patterns).
  - `app.rate-limit.enabled=false` short-circuits the filter entirely (`filterChain.doFilter` immediately).
  - This continued a previous, uncommitted iteration's partial work (`RateLimitFilter.java` + the `SecurityConfig` registration bean already existed on disk but didn't compile - wrong Jackson package, and an enum method illegally named `name()` shadowing `Enum.name()`, which is final); fixed both.
  - Found and fixed a second-order break: adding the filter to `SecurityConfig` made every existing `@WebMvcTest` that `@Import`s `SecurityConfig` (`AuthControllerTest`, `CoupleControllerTest`, `MatchControllerTest`, `MediaControllerTest`, `NotificationControllerTest`, `MediaTrackControllerTest`, `JwtAuthenticationFilterTest`) fail to build its context, since `RateLimitFilter`'s constructor needs `RateLimitService`/`RateLimitProperties`/`ClientIpResolver` beans that weren't in those tests' `@Import` lists - added all three to each.
  - Third-order break: with the filter live and no other changes, those same test classes (plus `SecurityConfigTest`) started getting real 429s, because default capacities (login 5/min, register 3/min) got exhausted by the many login/register calls spread across `@Test` methods sharing one cached context. Fixed by defaulting `app.rate-limit.enabled=false` in `src/test/resources/application.properties` and re-enabling it only in the new `RateLimitFilterTest` via `@TestPropertySource`.
- New integration test `RateLimitFilterTest` (`@SpringBootTest` + `@AutoConfigureMockMvc`, small capacities/windows via `@TestPropertySource`): blocking on each of the 4 endpoints, `Retry-After` header presence + plausible value, release after the window elapses, independent counters per `X-Forwarded-For` IP, and `GET /api/tracking`/`GET /api/auth/me` never rate-limited even under 10x volume.
- Files changed: `api/src/main/java/com/app/security/RateLimitFilter.java` (fixed), `api/src/main/java/com/app/security/SecurityConfig.java` (already had the registration bean, kept as-is), `api/src/test/resources/application.properties`, `api/src/test/java/com/app/security/RateLimitFilterTest.java` (new), and `@Import` list updates in `AuthControllerTest`, `CoupleControllerTest`, `MatchControllerTest`, `MediaControllerTest`, `NotificationControllerTest`, `MediaTrackControllerTest`, `JwtAuthenticationFilterTest`.
- `./mvnw test`: 383 tests, 0 failures, 0 errors; jacoco coverage gate passed.
- **Learnings for future iterations:**
  - US-003's per-account (email/user) limits live in `AuthService.login`/`CoupleService.joinCouple`, not the filter - the filter can't read the body without consuming the `InputStream` (explicitly forbidden from using `ContentCachingRequestWrapper` per the PRD). Those services should call `RateLimitService.tryConsume` directly with their own composed key, same as the filter does.
  - Any FUTURE `@WebMvcTest` for a controller behind `SecurityConfig` will need the same 3-class `@Import` addition (`ClientIpResolver`, `RateLimitService`, `RateLimitProperties`) - `RateLimitFilter` itself does NOT need to be in the `@Import` list, since `@WebMvcTest` auto-includes `Filter` beans by default.
  - If a new test class specifically needs to exercise rate limiting behavior with fast iteration, follow `RateLimitFilterTest`'s pattern: `@TestPropertySource` to flip `app.rate-limit.enabled=true` and shrink capacity/window for just that class, since the project-wide test default is now `false`.

## 2026-08-04 - US-003
- Implemented per-account rate limiting on top of US-002's per-IP filter: `AuthService.login` now consumes `"login:email:" + normalizedEmail` (via `RateLimitProperties.getLoginByEmail()`, default 10/hour) BEFORE looking up the user, so it fires even when the email doesn't exist (no enumeration oracle); `CoupleService.joinCouple` consumes `"couple-join:user:" + userId` (via `getCoupleJoinByUser()`, default 20/hour) as the first line of the method. Both reuse the existing generic `RateLimitService.tryConsume` (US-001) - no new bucket cache.
  - Email key is normalized (`trim().toLowerCase()`, null-safe) so case/whitespace variants share one bucket.
  - New `RateLimitExceededException` (`com.app.security`, carries `retryAfterSeconds`) is thrown by both services; `AuthExceptionHandler`/`CoupleExceptionHandler` each got an `@ExceptionHandler(RateLimitExceededException.class)` returning 429 + `Retry-After` header + `{"message": ...}`, matching `RateLimitFilter`'s format exactly. `@RestControllerAdvice(basePackages=...)` scopes by controller package, not exception package, so this works even though the exception type lives in `com.app.security`.
  - `AuthServiceTest`/`CoupleServiceTest` were converted to use REAL `RateLimitService`/`RateLimitProperties` instances (not mocks - bucket4j has no useful mock surface) via `@BeforeEach` for the default-limit case, plus a small helper (`newAuthServiceWithLoginByEmailLimit`/`newCoupleServiceWithJoinByUserLimit`) that builds a service with a shrunk `Limit` (capacity 1, short `Duration`) for dedicated exceed/release/case-insensitivity tests - keeps the rate-limit assertions fast (~300ms sleep) without affecting the shared default-capacity instance other tests use.
- Files changed: `api/src/main/java/com/app/security/RateLimitExceededException.java` (new), `api/src/main/java/com/app/auth/AuthService.java`, `api/src/main/java/com/app/auth/AuthExceptionHandler.java`, `api/src/main/java/com/app/couple/CoupleService.java`, `api/src/main/java/com/app/couple/CoupleExceptionHandler.java`, `api/src/test/java/com/app/auth/AuthServiceTest.java`, `api/src/test/java/com/app/couple/CoupleServiceTest.java`, `api/CLAUDE.md`.

- **Learnings for future iterations:**
  - This is the pattern to reuse for any other per-account limit (e.g. US-009's invite-code regenerate endpoint, which the PRD says should reuse "the US-003 infra"): compose a key, call `RateLimitService.tryConsume`, throw `RateLimitExceededException` on `!result.allowed()`, in the service method itself - never in a filter (filters can't read the body/authenticated principal cheaply per the US-002/US-003 constraint against `ContentCachingRequestWrapper`).

## 2026-08-04 - US-004
- Implemented timing-attack mitigation on `AuthService.login`: when `userRepository.findByEmail` returns empty, the method now calls `passwordEncoder.matches(request.password(), DUMMY_PASSWORD_HASH)` (result discarded) before throwing `InvalidCredentialsException`, so the unknown-email path spends roughly the same time as the wrong-password path (both now always call exactly one BCrypt `matches`). The error message and thrown exception type are unchanged in both cases (behavior preserved, only timing changed).
  - `DUMMY_PASSWORD_HASH` is a `private static final String` (computed once at class-load, never per-request) - a real BCrypt hash of an arbitrary password nobody uses, generated out-of-band with a one-off `BCryptPasswordEncoder(10).encode(...)` script (not committed) and pasted in as a literal, since generating it at runtime would defeat the point (it would just move the cost around, not remove it) and hashing at static-init time is effectively "once, ever," matching the PRD's "gerado uma unica vez" requirement.
  - Measured with a standalone microbenchmark (BCryptPasswordEncoder default strength 10, 100 iterations each, JIT-warmed): wrong-password path avg 60.124ms, unknown-email path avg 60.011ms - diff 0.19%, well under the 10% ceiling required by the acceptance criteria.
  - Added `docs/BACKLOG.md` decision D4 (new "Decisoes de Seguranca (Epico 5)" subsection under the existing decisions table): keep `409 Conflict` on `POST /api/auth/register` for duplicate email rather than a generic response, justified by the lack of transactional-email infra to close that oracle another way, mitigated by the existing per-IP rate limit on register (US-002, 3/min).
- Files changed: `api/src/main/java/com/app/auth/AuthService.java`, `api/src/test/java/com/app/auth/AuthServiceTest.java`, `docs/BACKLOG.md`.
- `./mvnw test`: 389 tests, 0 failures, 0 errors.
- **Learnings for future iterations:**
  - Any test that previously asserted `verify(passwordEncoder, never()).matches(...)` for an unknown-email login scenario is now WRONG - the whole point of US-004 is that `matches` IS called on that path. `AuthServiceTest.rejectsLoginWithUnknownEmail` was updated to assert `verify(passwordEncoder).matches(eq(request.password()), anyString())` instead, and a new `unknownEmailLoginInvokesPasswordEncoderAgainstDummyHash` test asserts the hash argument looks like a real BCrypt hash (`startsWith("$2a$")`). The two existing per-account rate-limit tests that hit the unknown-email path twice (once allowed, once rate-limited) needed their `never()` assertion changed to `times(1)`, since only the FIRST call reaches the password check - the second is rejected by `enforceLoginRateLimit` before `findByEmail` even runs.
  - To generate a real BCrypt hash string outside the Spring context (e.g. for a literal constant), compile a throwaway `.java` file against just `spring-security-crypto` + `commons-logging` + `spring-core` + `spring-jcl` from `~/.m2` (`BCryptPasswordEncoder` needs `org.springframework.util.StringUtils` at runtime, which is NOT in `spring-security-crypto` itself) - faster than spinning up a Spring context or a Maven test just to print one string.
  - US-005 is next: `LoginRequest` validation (`@NotBlank`/`@Email`) plus `RegisterRequest.password` size cap - a good next place to also verify no regression was introduced in this story's "malformed email still returns 401 today" behavior, since US-005 changes that to 400.
