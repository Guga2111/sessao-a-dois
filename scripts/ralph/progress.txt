## Codebase Patterns
- `client/`: dark theme prototype colors are historically inlined via Tailwind arbitrary values (`bg-[#161513]`, etc.) — see `client/CLAUDE.md`. As of Epico 13/US-001, `client/src/index.css` now carries the *real* brand palette as semantic tokens (`.dark` block), so future color-migration stories (US-003+) should map hex -> token per the list in that file's comment, not invent new arbitrary values.
- The app is dark-only in practice (D17, `POST-MVP-TASK.md`): the `ThemeProvider`/`d`-key toggle to light mode still exists in code but produces a broken UI, since every screen hardcodes dark hex regardless of theme. Removing that toggle is a separate future story (T13.3) — don't touch `:root` (light) tokens for color-migration work, only `.dark`.
- Hex/oklch round-trip check: convert with the standard sRGB<->OKLCH matrices (D65, CSS Color 4), round L/C/H to 3 decimals, then convert back and diff per-channel — 1 unit of rounding tolerance is expected and acceptable.
- `bun run typecheck`/`lint`/`test:run`/`build` are all run from `client/` (that's where `package.json` lives), not the repo root.

- **Learnings for future iterations:**
  - **Big one:** every subsequent per-file migration story (US-004 onward) should expect the same shape of problem — files almost certainly have hex/rgba values beyond the 8 tokens US-001 established (US-001 only tokenized the 8 *most frequent* hexes app-wide, not every color any single file happens to use). When that happens: migrate what maps, leave what doesn't (don't invent), note the leftover values in the story's `notes` field — but do **NOT** remove the file from `color-migration-allowlist.txt` if any raw color remains, or `check:colors` in CI breaks. Only pull a file off the allowlist once `node scripts/check-color-literals.mjs --list-offenders` (from `client/`) no longer lists it.
  - `rgba(255,255,255,.1)` (10% white) already has an exact semantic match: the `--border` token (`oklch(1 0 0 / 10%)` in `.dark`) — use `border-border`, not an arbitrary value, whenever you see that exact alpha. `.05` and `.06` white/black rgba values are *not* the same token (different alpha) — don't round them into `--border` just because they're visually close; that would move a pixel to save a token.
  - Inline `style={{ background: "#hex" }}` (not a Tailwind className) can still trip `check-color-literals.mjs` — its `HEX_RE` matches any `#rrggbb` in the line, class or not. If the hex matches a known token, swap it for `style={{ background: "var(--token-name)" }}` (same prop, same structure) rather than trying to force it into a className.
  - A recurring color family worth flagging for a future US-001 follow-up (not done here, per "don't invent tokens" rule): `#ffdd7a`/`rgba(255,255,255,.05)`/`#d6d2c8` form a "shared vs. not-shared pill" pattern that shows up identically in both the genres and watch-providers sections of `ComparisonDialog.tsx` — likely reused verbatim in other match/comparison components too, so a real token pair for it (e.g. something like `--pill-shared`/`--pill-neutral`) would clean up several files at once instead of one at a time.
  - Next priority story is US-004 (`MediaDetailModal.tsx`, 103 occurrences) — same mechanical approach; check first whether it shares any of the untokenized colors found here (`#ffb443`, `#3ddc97`, `#d6d2c8`, `#c4bfb4`, `#2b2920`, `#111` are all plausible prototype-wide constants, not one-off local values).
