## Codebase Patterns
- `client/`: dark theme prototype colors are historically inlined via Tailwind arbitrary values (`bg-[#161513]`, etc.) — see `client/CLAUDE.md`. As of Epico 13/US-001, `client/src/index.css` now carries the *real* brand palette as semantic tokens (`.dark` block), so future color-migration stories (US-003+) should map hex -> token per the list in that file's comment, not invent new arbitrary values.
- The app is dark-only in practice (D17, `POST-MVP-TASK.md`): the `ThemeProvider`/`d`-key toggle to light mode still exists in code but produces a broken UI, since every screen hardcodes dark hex regardless of theme. Removing that toggle is a separate future story (T13.3) — don't touch `:root` (light) tokens for color-migration work, only `.dark`.
- Hex/oklch round-trip check: convert with the standard sRGB<->OKLCH matrices (D65, CSS Color 4), round L/C/H to 3 decimals, then convert back and diff per-channel — 1 unit of rounding tolerance is expected and acceptable.
- `bun run typecheck`/`lint`/`test:run`/`build` are all run from `client/` (that's where `package.json` lives), not the repo root.
- Per-file color migration mechanical rules (established US-003, confirmed US-004/US-005/US-006): (1) `bg-[rgba(R,G,B,X)]`/`border-[rgba(R,G,B,X)]` whose R,G,B exactly equals a known token's hex (e.g. `rgba(255,203,43,X)`=`#ffcb2b`=primary, `rgba(255,107,107,X)`=`#ff6b6b`=destructive, `rgba(9,9,10,X)`=`#09090a`=background — confirmed in US-006) converts to `token-name/X` for *any* alpha X — the Tailwind opacity modifier handles the alpha, no exact-alpha match needed. (2) Reusing a *named* semantic token for a *different* CSS property (e.g. `--border` for a `bg-` utility) DOES require an exact alpha match — `rgba(255,255,255,.1)` → `border-border` is valid (exact `--border` value), but `bg-[rgba(255,255,255,.05)]`/`.06`/`.07`/`.08`/`.15` has no token yet and must stay untouched, don't round it into `--border`. (3) A hex value that lives outside a Tailwind className (a plain JS object field, or a `style={{ background: "#hex" }}` inline style) that matches a known token still needs migrating — swap it for `"var(--token-name)"` (same prop/structure), don't leave it just because it's not in a `className`.
- Chart/series color exception (US-007, `DashboardScreen.tsx`): unlike the default "no token → leave hex, note it" fallback, a story's AC can explicitly require chart/graph series colors with no semantic match to use `--chart-1`..`--chart-5` (present in `index.css` but, as of US-007, still unused by any `.tsx` and still the raw shadcn grayscale preset — no brand mapping documented) instead of staying hex — this intentionally breaks pixel-identity for that one series and is scoped only to literal chart/graph fills (donut segments, bar fills), not to icon/label accents that happen to share the same hex. Always check for a story-specific AC bullet like this before applying the generic fallback; `check-color-literals.mjs`'s `HEX_RE`/`ARBITRARY_COLOR_RE` never flag a bare `rgba(...)` outside a Tailwind arbitrary-utility bracket, so those can stay untouched in a gradient string even when a token would technically match — only literal `#hex` and `token-[...]` bracket usages are gated.
- **Correction to a US-004/US-005 claim (found US-008):** `ARBITRARY_COLOR_RE` (`/\b(?:bg|text|border|ring|from|to|via|shadow|fill|stroke)-\[[^\]]*\]/g`) does **not** check the bracket's *content* — it matches `text-[13px]`/`text-[22px]`/`text-[clamp(...)]` (font sizes) exactly the same as it matches `text-[#a6a39a]` (an actual color), because it only looks for the prefix + `-[`. The earlier note ("non-color arbitrary utilities … are not matched by the regexes") was imprecise: they *are* matched, they just don't map to any of the 8 tokens (font size isn't a color), so they fall into the same "leave it, it's leftover" bucket as an untokenized hex — the practical outcome (untouched, file stays allowlisted) is identical either way, but don't reason from "the regex ignores font sizes" when deciding what a future story is allowed to touch.
- `border-white/10`/`hover:bg-white/[0.06]`/`hover:text-white` (Tailwind's built-in named `white` color, with a plain `/N` opacity modifier or a bracketed *opacity* value) are never flagged by either regex — `ARBITRARY_COLOR_RE` requires the literal sequence `-[` right after the utility prefix, and `white` isn't inside brackets, only the opacity number is. These are common in modal/input borders (`TitleModal.tsx`, confirmed US-008) and are correctly out of migration scope even though `border-white/10` is visually identical to `border-border` (`--border: oklch(1 0 0 / 10%)`) — don't "fix" them into `border-border` on your own initiative, the AC only requires migrating what the gate actually flags.
