## Codebase Patterns
- Backend: `./mvnw -B test` is the gate; it also runs JaCoCo (min 90% line coverage on BUNDLE). A build is not done until this is green.
- `api/src/test/resources/application.properties` REPLACES (not merges with) `api/src/main/resources/application.properties` for any `@SpringBootTest`. Any new property an eagerly-instantiated bean depends on must be mirrored there.
- Before referencing any Spring Boot 4.1 auto-configuration/endpoint class by name, verify the real package in the jar first (`unzip -l ~/.m2/repository/org/springframework/boot/<artifact>/4.1.0/*.jar | grep <Class>`) — Boot 4.1 moved packages around vs. 3.x docs/examples.
- `SecurityConfig` applies `anyRequest().authenticated()`, which runs at the Spring Security filter level BEFORE DispatcherServlet tries to map a route. So an unmapped route under a closed `/actuator/**` exposure still returns 401 (via the app's `authenticationEntryPoint`), not 404 — test the status the app actually returns, don't assume 404 just because "nothing is mapped there".
- A `@SpringBootTest @AutoConfigureMockMvc` test that does NOT call `SecurityMockMvcRequestPostProcessors.csrf()` does not need `@DirtiesContext` — the context-poisoning gotcha documented on `SecurityConfigTest` only applies to tests that use that specific helper.

## 2026-08-13 - US-009
- Implemented: a new `notify-failure` job in `.github/workflows/deploy.yml`, sending a Resend email whenever `tests` (CI) or `deploy` fails on a push to `main`/manual dispatch. Success sends nothing (`if: failure()`). The job is separate from `deploy` on purpose — if `tests` fails, `deploy` is `skipped` (not `failure`), so any step nested inside `deploy` with `if: failure()` would never run and the most common failure (red CI) would go unreported; a job with `needs: [tests, deploy]` + `if: failure()` catches both.
- Files changed:
  - `.github/workflows/deploy.yml`: added the `notify-failure` job. It reads `needs.tests.result`/`needs.deploy.result` to name the job that actually failed ("tests (CI)" when `tests` isn't `success`, else "deploy"), builds the email body with `printf` (plain multi-line string, no JSON at this stage), then hands `from`/`to`/`subject`/`text` to `jq -n --arg ...` to produce the JSON payload — never string-interpolated directly, so an arbitrary commit message or branch name can't break the JSON (branch/commit aren't even used for anything riskier than plain text here, but the mechanism is the same one that would matter if they were). Recipient comes from new secret `ALERT_EMAIL_TO`; if it's unset the job fails fast with an explicit message before ever calling `curl` (mirrors the existing `for var in ...; do if [[ -z "${!var}" ]]; then ...` pattern already used in the `deploy` job's "Escrever .env" step). Sender (`EMAIL_FROM`) and auth (`RESEND_API_KEY`) reuse the exact same secret/variable the `deploy` job already writes into `.env` for `com.app.email.ResendEmailSender` — no new provider, no new cost (E12.4). `curl -fsS ... > /dev/null` so a non-2xx Resend response fails the step loudly without echoing the response body into the log.
  - `docs/DEPLOY.md`: added `ALERT_EMAIL_TO` to the GitHub secrets table, with an explicit note that it's the one exception to the "três lugares" rule documented earlier in the same file (`docs/DEPLOY.md:144-151`) — it's consumed only by the workflow, never written into the VPS `.env` or `docker-compose-prod.yml`'s `environment:`, because no container needs it.
  - `scripts/ralph/prd.json`: US-009 `passes` set to `true`.
- Verification: `./mvnw -B test` — 585 tests, 0 failures, 0 errors, JaCoCo coverage check passed, BUILD SUCCESS (unchanged count, as expected — no backend code touched by this story). Validated the new job's YAML by loading the file with `js-yaml` (borrowed from `client/node_modules`, since no top-level `package.json` in this repo has it) and inspecting the parsed `jobs.notify-failure` structure. Independently re-derived the `jq -n --arg` payload-building logic in an isolated `bash -c '...'` sandbox script (not the real workflow) with a deliberately hostile `COMMIT_SHA` containing an embedded `"` and `;`, confirmed the resulting JSON parses cleanly with `jq .` and that the hostile content lands as inert string content inside `"text"`, never breaking the JSON structure or executing.
- **Testado com falha forçada em run real do GitHub Actions: GATE HUMANO, não executado.** Este agente não consegue disparar uma run real do `deploy.yml` a partir do sandbox (exigiria push/PR na `main` real ou `workflow_dispatch` contra o repositório no GitHub, ambos fora do alcance daqui). Como fazer, para quem for validar manualmente:
  1. **Simular falha da CI:** numa branch de teste, quebrar deliberadamente um teste (`api` ou `client`) e abrir/mergear um PR que dispare o `deploy.yml` via `workflow_dispatch` (ou mergear para `main` num fork/branch de teste, se disponível) — confirmar que `tests` fica `failure`, `deploy` fica `skipped`, e o e-mail chega com "Job que falhou: tests (CI)".
  2. **Simular falha do deploy:** adicionar temporariamente um step `run: exit 1` em qualquer ponto do job `deploy` (ex.: logo após o checkout) numa branch de teste, disparar via `workflow_dispatch`, confirmar `tests: success` / `deploy: failure` e "Job que falhou: deploy" no e-mail — depois reverter o step.
  3. **Confirmar run verde não dispara nada:** qualquer deploy bem-sucedido normal já serve de prova negativa (nenhum e-mail chegou nas runs anteriores a esta story, que sempre passaram).
  4. Antes de qualquer um desses testes, configurar o secret `ALERT_EMAIL_TO` em Settings > Secrets and variables > Actions (nível repo ou environment `production`) — sem ele o job falha explicitamente no próprio `notify-failure`, o que também é um teste válido do guard-rail (mas não do envio de e-mail em si).
- **Learnings for future iterations:**
  - `needs.<job>.result` is readable by any job in the workflow that lists `<job>` in its own `needs`, even when that job was `skipped` (value is literally the string `"skipped"`) — no special handling needed to read a skipped dependency's result, just don't assume it's always `"success"`/`"failure"`.
  - `zsh`'s builtin `echo` interprets `\n` as a real newline by default (unlike `bash`'s `echo`, which needs `-e` for that) — this bit while manually sanity-checking the `jq -n --arg` construction in this sandbox's zsh shell: `echo "$PAYLOAD" | jq .` failed with `Invalid string: control characters...` even though the payload was correctly escaped, because zsh's `echo` had already converted the embedded `\n` into a literal newline before `jq` ever saw it. Confirmed the payload was fine all along by re-running the identical check via `bash -c '...'` (GitHub Actions `run:` steps default to `bash`, not `zsh`, so this was purely a local-verification artifact, not a bug in the workflow). Worth remembering for anyone manually eyeballing `jq`-built JSON in this sandbox's default shell — use `printf '%s\n' "$VAR" | jq .` or an explicit `bash -c` wrapper instead of `echo`, or the false alarm repeats.
  - No `js-yaml`/`yamllint`/`actionlint` binary is installed at the top level of this repo; `client/node_modules/js-yaml` (a transitive dependency of something in `client/`) works fine as an ad-hoc YAML-parse sanity check for `.github/workflows/*.yml` changes via `node -e "require('./client/node_modules/js-yaml')..."` when no dedicated linter is available.
