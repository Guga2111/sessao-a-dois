## Codebase Patterns
- This sandbox has no `docker`, `java`, `mvn`, or `psql` — `./mvnw` cannot run here (no JDK). Backend "Typecheck passes"/"Tests pass" criteria that require compiling/running the Spring Boot app cannot be verified in this environment; note that limitation explicitly in progress/notes instead of silently skipping it. `api/CLAUDE.md` already documents this.
- There is no Flyway/Liquibase yet on `create-migrations`'s baseline — schema currently evolves via `spring.jpa.hibernate.ddl-auto=update`. Entities: `com.app.user.User`, `com.app.couple.Couple`, `com.app.tracking.MediaTrack` (+`media_track_genre` via `@ElementCollection`), `com.app.tracking.UserReview`, `com.app.match.MatchLike`/`MatchReject`, `com.app.notification.Notification` (new, not in `origin/main`).
- The `/ralph` skill (`.claude/skills/ralph/SKILL.md`) writes its converted `prd.json` into its own skill directory (`.claude/skills/ralph/`), which is a DIFFERENT directory from the one the running Ralph loop actually reads (`scripts/ralph/`, per `scripts/ralph/CLAUDE.md`: "same directory as this file"). If `scripts/ralph/prd.json` is ever found empty/stale after running `/ralph`, check `.claude/skills/ralph/prd.json` for the real converted content and copy it over before doing anything else — do not treat an empty `prd.json` as "PRD not ready yet" without checking there first.
- `git diff origin/main HEAD -- <entity file>` is a fast way to confirm whether a JPA entity actually changed between the deployed baseline and the current branch, instead of trusting a PRD's claims at face value.

## [2026-08-01] - US-003
- Implemented: switched schema management fully to Flyway across both classpath roots. `api/src/main/resources/application.properties`: `spring.jpa.hibernate.ddl-auto` changed from `update` to `validate`; added `spring.flyway.enabled=true`, `spring.flyway.baseline-on-migrate=true`, `spring.flyway.baseline-version=1`, `spring.flyway.locations=classpath:db/migration`. `api/src/test/resources/application.properties`: mirrored the same 4 Flyway properties + `ddl-auto=validate`, and additionally added an explicit `spring.datasource.url=jdbc:h2:mem:testdb;MODE=PostgreSQL;DATABASE_TO_LOWER=TRUE` + `spring.datasource.driver-class-name=org.h2.Driver` — previously the test datasource had no explicit URL and relied on Spring Boot autodetecting a plain embedded H2, which would not understand the Postgres-flavored SQL (UUID types, etc.) that V1/V2 migrations will use once they exist. Confirmed via grep that no `ddl-auto=update` remains anywhere in `api/src`. Deliberately did NOT add a `flyway-database-h2` dependency to `pom.xml`: H2 (like HSQLDB/Derby/SQLite) ships bundled inside `flyway-core` itself; only PostgreSQL/MySQL/etc. need the separate `flyway-database-*` module, which US-002 already added for Postgres.
- Files changed: `api/src/main/resources/application.properties`, `api/src/test/resources/application.properties`, `scripts/ralph/prd.json` (US-003 `passes: true`), `.claude/skills/ralph/prd.json` (mirrored), `scripts/ralph/progress.txt`.
- **Learnings for future iterations:**

This is expected and self-resolves once US-004 (`V1__baseline.sql`) and US-005 (`V2__create_notification.sql`) land — do not try to "fix" this by reverting to `update` or by pre-creating a migration file out of order; just proceed to US-004 next.
