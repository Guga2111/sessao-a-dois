## Codebase Patterns
- MediaTrack -> UserReview is already `@OneToMany(mappedBy = "mediaTrack", cascade = CascadeType.ALL, orphanRemoval = true)` (api/src/main/java/com/app/tracking/MediaTrack.java), so `MediaTrackRepository.delete(track)` already cascades review deletion with no orphan rows. No new repository/service code was needed for cascade delete, only test coverage.
- MediaTrackService.findOwnedTrack(trackId, coupleId) is the shared ownership-check helper (throws generic `ResourceNotFoundException("titulo nao encontrado")` for both "does not exist" and "belongs to another couple") - reuse this pattern for any new endpoint that must be couple-scoped rather than writing a new lookup.
- This sandbox has no JDK/Maven available (`./mvnw` fails: no `java`, no cached Maven distribution, no network to Maven Central) - `./mvnw test` could not be executed here. Changes were verified by careful manual review only. Flag this to a human or run in an environment with JDK 21 + Maven Central access before merging.
- To split one `GET` endpoint into an "old shape" vs "new shape" response depending on an optional query param, use `@GetMapping(params = "!status")` / `@GetMapping(params = "status")` on two separate handler methods instead of branching return type inside one method (Spring dispatches by presence of the param, and each method keeps a single concrete `ResponseEntity<T>` type). `MediaTrackController.list`/`listByStatus` (GET /api/tracking) is the example.
- For paginated repository queries, add a second finder overload alongside the existing unpaged one (`findByCoupleIdAndStatus(UUID, MediaStatus)` unpaged vs `findByCoupleIdAndStatusOrderByCreatedAtDesc(UUID, MediaStatus, Pageable)` paged) rather than changing the existing method's signature - Spring Data resolves by parameter list, so both can coexist and old callers are untouched. Clamp caller-supplied `page`/`size` server-side in the service (`Math.max(page, 0)`, `Math.min(Math.max(size, 1), MAX_PAGE_SIZE)`) before building the `Pageable`, never trust them raw.
- `@DataJpaTest` repository tests that assert ordering by a Hibernate `@CreationTimestamp` column need a real time gap between inserts (`mediaTrackRepository.flush()` then `Thread.sleep(5)` between each `save`) - otherwise multiple rows saved in the same test can get identical timestamps and the sort order becomes flaky.
- As of 2026-07-23 `npm run dev` in `client/` actually starts fine in this sandbox (the previously-documented rolldown native-binding failure is no longer reproducing) - try it before assuming it's broken. The API still has no JDK/Maven here though, so full frontend+backend browser verification still isn't possible, only static rendering checks.
