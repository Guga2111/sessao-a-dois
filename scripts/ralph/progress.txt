## Codebase Patterns
- Backend: package-by-feature under `com.app.<feature>` (e.g. `com.app.user`), see docs/ARCHITECTURE.md.
- `spring.jpa.hibernate.ddl-auto=update` (api/src/main/resources/application.properties) — no manual migrations; entities drive schema creation against the dev PostgreSQL.
- This sandbox has no JDK/`java`/`mvn` and no network access to Maven Central — `./mvnw` cannot be run here (see api/CLAUDE.md). Implement carefully and double-check imports/APIs by hand; a JDK-enabled environment must verify the build before merge.
- For repository-level JPA tests, use `@DataJpaTest` with the `com.h2database:h2` dependency added in test scope (api/pom.xml) — Spring Boot auto-swaps in an embedded DB, no extra config needed.
- `@WebMvcTest` auto-includes `Filter` beans (e.g. `JwtAuthenticationFilter`), so any `@WebMvcTest(...) @Import(SecurityConfig.class)` slice must also `@MockitoBean` every bean that filter depends on (currently `JwtService`), even for controllers unrelated to auth.
- Frontend (client/): this sandbox has no `bun` binary, only `node`/`npm`. `npm install` works (registry is reachable) and is fine for adding deps/running `tsc --noEmit`/`eslint`, but do NOT commit a generated `package-lock.json` (project uses `bun.lock`) — delete it after installing. `bun.lock` itself can't be regenerated here; note in progress.txt that a bun-enabled environment must run `bun install` to sync it after any `client/package.json` dependency change.
- Frontend (client/): `vite build` / `bun run build` fails in this Linux sandbox with "Cannot find module '@rolldown/binding-linux-arm64-gnu'" — `node_modules` only has `@rolldown/binding-darwin-arm64` from the original Mac-side `bun install`. This is a pre-existing sandbox limitation, not a real bug; verified via `git stash` that it fails identically on unmodified code. Rely on `tsc --noEmit` + `eslint .` as the quality gates here instead of a full build; a real build must be verified on a properly provisioned machine (or in CI) before merge.

## 2026-07-20 - US-004
- Replaced the Epico-1 permit-all `SecurityConfig` (`com.app.security`) with the real config: `SessionCreationPolicy.STATELESS`, CORS (`app.cors.allowed-origin`, default `http://localhost:5173`, env-overridable via `CORS_ALLOWED_ORIGIN`), public routes `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/health` via `requestMatchers`, everything else `authenticated()`.
- Added `JwtAuthenticationFilter` (`com.app.security`, `OncePerRequestFilter`): reads `Authorization: Bearer <token>`, calls `JwtService.parseSubject`, and on success sets a `UsernamePasswordAuthenticationToken(userId, null, List.of())` on the `SecurityContextHolder`. On missing/invalid/expired token it just clears context and continues the chain — no attempt to write a response here; unauthenticated requests hitting a protected route get rejected downstream.
- Configured `exceptionHandling().authenticationEntryPoint(...)` to `response.sendError(401)` — without this, Spring Security's default entry point for a stateless config with `formLogin`/`httpBasic` disabled returns 403, not 401, for unauthenticated access to a protected route.
- Files changed: api/src/main/java/com/app/security/{SecurityConfig.java (modified), JwtAuthenticationFilter.java (new)}, api/src/main/resources/application.properties (added `app.cors.allowed-origin`), api/src/test/java/com/app/auth/AuthControllerTest.java (added `@MockitoBean JwtService`), api/src/test/java/com/app/security/JwtAuthenticationFilterTest.java (new), scripts/ralph/prd.json.
- **Learnings for future iterations:**
  - `@WebMvcTest` auto-detects `Filter` beans (per Spring Boot docs, the slice includes `@Controller`, `@ControllerAdvice`, converters, and `Filter`), so `JwtAuthenticationFilter` (a `@Component` implementing `Filter` via `OncePerRequestFilter`) gets pulled into *every* `@WebMvcTest` slice that also `@Import(SecurityConfig.class)` — even slices unrelated to auth. Since the filter's constructor needs `JwtService`, any such test now needs `@MockitoBean private JwtService jwtService;` or the context fails to start. Remember this for US-005/US-006 controller tests (couple endpoints will be genuinely protected, so they'll need this anyway plus a way to stub an authenticated principal — see next point).
  - No dedicated protected domain endpoint exists yet in this epic (couple endpoints come in US-005/US-006), so `JwtAuthenticationFilterTest` declares a tiny nested `@RestController` test-fixture (`GET /api/test/protected`) via `@WebMvcTest(controllers = ...ProtectedTestController.class)` to exercise the authorization + filter behavior end-to-end. Once real protected controllers exist, prefer testing against them directly instead of adding more fixture controllers.
  - The filter sets the JWT subject `UUID` as the `Authentication` principal directly (no `User`/`UserDetails` lookup) — cheap and sufficient since nothing yet needs full user data from the security context. If a future story needs `@AuthenticationPrincipal` to resolve to a richer object, that's a deliberate change to `JwtAuthenticationFilter`, not a gap.
  - Still no JDK/`mvn`/network in this sandbox — could not run `./mvnw test`. Re-verify with a real JDK 21 environment before merge.
