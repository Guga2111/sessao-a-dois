## Codebase Patterns
- `@ConfigurationProperties` classes in this codebase are plain `@Component` beans (no `@EnableConfigurationProperties`/`@ConfigurationPropertiesScan` registered anywhere) - component scan picks them up because they live under `com.app`.
- bucket4j 8.10.1 (`com.bucket4j:bucket4j-core`, Java package `io.github.bucket4j`) API used: `Bucket.builder().addLimit(Bandwidth.classic(capacity, Refill.intervally(capacity, window))).build()`, then `bucket.tryConsumeAndReturnRemaining(1)` -> `ConsumptionProbe.isConsumed()`/`getNanosToWaitForRefill()`. A record component accessor cannot share a zero-arg signature with a static factory method of the same name on that record (e.g. `record R(boolean allowed)` cannot also declare `static R allowed()`) - javac reports it as "invalid accessor method... must be public", which is misleading; rename the static factory instead.
- `@WebMvcTest(SomeController.class)` only loads the controller + explicitly `@Import`ed beans - any plain `@Component` a controller depends on (e.g. `ClientIpResolver`) must be added to the test's `@Import({...})` list or the context fails to wire it. EXCEPTION: a `@Component` that also implements `jakarta.servlet.Filter` (e.g. `RateLimitFilter`) IS auto-included by `@WebMvcTest`'s default slice scanning even without an explicit `@Import` - Filter beans are one of the types `@WebMvcTest` picks up by default (along with `@Controller`, `@ControllerAdvice`, `@JsonComponent`, `WebMvcConfigurer`). Its own constructor dependencies (`RateLimitService`, `RateLimitProperties`, `ClientIpResolver`) still need explicit `@Import` though, since those are plain `@Component`s, not Filters.
- Spring Boot 4.1 moved Jackson to **Jackson 3** (`tools.jackson.core:jackson-databind`, package `tools.jackson.databind.*`) as the framework-managed one; `com.fasterxml.jackson.databind.ObjectMapper` (Jackson 2, package `com.fasterxml.jackson.databind`) is only pulled in transitively at runtime scope by `jjwt-jackson` and is NOT on the compile classpath. Any new code that needs to inject the Spring-managed `ObjectMapper` bean (e.g. to hand-write a JSON body in a raw servlet `Filter`, outside Spring MVC's message converters) must import `tools.jackson.databind.ObjectMapper`, not the `com.fasterxml` one.
- In-memory rate-limit/cache services that key by arbitrary strings (IP, email, user id) should evict inactive entries via a `@Scheduled` sweep (app already has `@EnableScheduling` on `SessaoADoisApplication`) rather than relying on an external cache library - keeps the dependency footprint small for a single-instance 1 CPU / 512M deployment.
- `api/src/test/resources/application.properties` sets `app.rate-limit.enabled=false` by default (US-002) - since it REPLACES main's `application.properties` for every `@SpringBootTest`/`@WebMvcTest` context, and `RateLimitFilter` is auto-included in every `@WebMvcTest` slice (see point above), leaving rate limiting on by default would make unrelated test classes that call login/register repeatedly across many `@Test` methods in the same class (sharing one cached Spring context, hence one singleton `RateLimitService` bucket map, hence one `127.0.0.1` IP key) trip the low default caps (register 3/min, login 5/min) and get spurious 429s. Any test that needs rate limiting actually active (like `RateLimitFilterTest`) re-enables it locally via `@TestPropertySource(properties = "app.rate-limit.enabled=true")` plus small capacities/windows (e.g. `2` / `3s`) so exceed/release assertions run in seconds, not real default windows of 1 minute/1 hour.

## 2026-08-04 - US-004
- Implemented timing-attack mitigation on `AuthService.login`: when `userRepository.findByEmail` returns empty, the method now calls `passwordEncoder.matches(request.password(), DUMMY_PASSWORD_HASH)` (result discarded) before throwing `InvalidCredentialsException`, so the unknown-email path spends roughly the same time as the wrong-password path (both now always call exactly one BCrypt `matches`). The error message and thrown exception type are unchanged in both cases (behavior preserved, only timing changed).
  - `DUMMY_PASSWORD_HASH` is a `private static final String` (computed once at class-load, never per-request) - a real BCrypt hash of an arbitrary password nobody uses, generated out-of-band with a one-off `BCryptPasswordEncoder(10).encode(...)` script (not committed) and pasted in as a literal, since generating it at runtime would defeat the point (it would just move the cost around, not remove it) and hashing at static-init time is effectively "once, ever," matching the PRD's "gerado uma unica vez" requirement.
  - Measured with a standalone microbenchmark (BCryptPasswordEncoder default strength 10, 100 iterations each, JIT-warmed): wrong-password path avg 60.124ms, unknown-email path avg 60.011ms - diff 0.19%, well under the 10% ceiling required by the acceptance criteria.
  - Added `docs/BACKLOG.md` decision D4 (new "Decisoes de Seguranca (Epico 5)" subsection under the existing decisions table): keep `409 Conflict` on `POST /api/auth/register` for duplicate email rather than a generic response, justified by the lack of transactional-email infra to close that oracle another way, mitigated by the existing per-IP rate limit on register (US-002, 3/min).
- Files changed: `api/src/main/java/com/app/auth/AuthService.java`, `api/src/test/java/com/app/auth/AuthServiceTest.java`, `docs/BACKLOG.md`.
- `./mvnw test`: 389 tests, 0 failures, 0 errors.
- **Learnings for future iterations:**
  - Any test that previously asserted `verify(passwordEncoder, never()).matches(...)` for an unknown-email login scenario is now WRONG - the whole point of US-004 is that `matches` IS called on that path. `AuthServiceTest.rejectsLoginWithUnknownEmail` was updated to assert `verify(passwordEncoder).matches(eq(request.password()), anyString())` instead, and a new `unknownEmailLoginInvokesPasswordEncoderAgainstDummyHash` test asserts the hash argument looks like a real BCrypt hash (`startsWith("$2a$")`).
