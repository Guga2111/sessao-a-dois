## Codebase Patterns
- User references on entities scoped to a Couple (recipientUserId, actorUserId, MatchLike.userId) are plain UUID @Column fields, not @ManyToOne to User — only the Couple relation is a real JPA association.
- This sandbox has no JDK/Maven (`mvn`/`java` missing, `./mvnw` can't reach Maven Central) — backend changes here cannot be compiled/tested locally; mirror existing tested code closely and flag verification as pending.
- Derived Spring Data `deleteBy...` repository methods (e.g. `deleteByCreatedAtBefore`) return a long/int count of deleted rows and need no `@Modifying` — just call them from a `@Transactional` service method.
- `@CreationTimestamp` fields (like `Notification.createdAt`) can't be set via the constructor in tests; use `ReflectionTestUtils.setField(entity, "createdAt", ...)` after `save()` (then `saveAll`) to backdate a row for retention/expiry tests.

## 2026-07-26 - US-003
- Implemented: NotificationDto + NotificationService with per-recipient persistence and after-commit STOMP broadcast to /topic/couple/{coupleId}/notifications.
- Files changed:
  - api/src/main/java/com/app/notification/NotificationDto.java (new)
  - api/src/main/java/com/app/notification/NotificationService.java (new)
  - api/src/main/java/com/app/websocket/WebSocketConfig.java (Javadoc only — /topic broker already covers the new destination, no functional change needed)
  - api/src/test/java/com/app/notification/NotificationServiceTest.java (new)
- **Learnings for future iterations:**
  - `NotificationService.notifyCouple(couple, type, tmdbId, mediaType, title, actorUserId)` is the single entry point future stories (US-004 match flow, US-005 no-match flow) should call from within their existing @Transactional method — it persists one Notification per couple member (from `couple.getUser1Id()`/`getUser2Id()`, skipping null) and returns the list of DTOs.
  - STOMP broadcast happens inside `TransactionSynchronization.afterCommit()` registered via `TransactionSynchronizationManager.registerSynchronization(...)` when `isSynchronizationActive()` — this defers the push until the enclosing @Transactional method's transaction actually commits, satisfying "notificacao ja existe no banco quando o push chega". Falls back to immediate `broadcast()` if no transaction is active (e.g. called outside a transactional context, or in a plain unit test with Mockito — MockitoExtension has no real transaction, so `isSynchronizationActive()` is false there and the send happens synchronously, which is why NotificationServiceTest can assert on `messagingTemplate` directly without simulating a commit).
  - actorName is resolved via `UserRepository.findById(actorUserId).map(User::getName).orElse(null)` — reuse this instead of re-querying User elsewhere; falls back to null if the actor user record is somehow missing (should not happen in practice but avoids an NPE/exception path).
  - One STOMP message is sent per created Notification DTO (so a couple event with 2 recipients sends 2 messages to the same topic) rather than a single combined event — mirrors "creates duas Notification ... retorna os DTOs" from the story literally. Future frontend work (US-008) must be aware both members' STOMP clients will observe both DTOs on the shared topic; frontend must NOT blindly push every incoming DTO into the current user's list without checking it's meant for them if that becomes an issue in practice — revisit if US-008 finds this creates duplicate/wrong entries for a user's own notification.
  - Same sandbox limitation as prior stories: no JDK/Maven available, so `./mvnw test` could not be run — code mirrors MatchService/MatchServiceTest patterns closely (constructor injection, Mockito unit test with ArgumentCaptor) to minimize risk. Verify on a machine with JDK 21 + Maven Central access.

## 2026-07-26 - US-004
- Implemented: Match flow now creates MATCH notifications for both couple members via NotificationService.
- Files changed:
  - api/src/main/java/com/app/match/MatchService.java (constructor now takes NotificationService; createMatch(couple, request, actorUserId) calls notificationService.notifyCouple(couple, NotificationType.MATCH, tmdbId, mediaType, title, actorUserId) after the MediaTrack save + existing /match STOMP send)
  - api/src/test/java/com/app/match/MatchServiceTest.java (added NotificationService mock; asserted notifyCouple call args on both match-producing tests, and never-called on the "already matched, no duplicate track" test)
- **Learnings for future iterations:**
  - `actor_user_id` for a MATCH notification is the `userId` param of `MatchService.like(coupleId, userId, request)` — i.e. whichever user's `like()` call is the one that discovers the partner already liked the same tmdb_id (closes the match), not the first liker. This is naturally already the `userId` in scope inside `createMatch`, no extra lookup needed.
  - `createMatch` already ran inside the caller's `@Transactional like()` method, so no new transaction boundary was needed for `NotificationService.notifyCouple(...)` — its own after-commit STOMP scheduling (see Codebase Patterns / api/CLAUDE.md) attaches to that same transaction automatically.
  - `MatchService`'s existing `/topic/couple/{id}/match` STOMP send (via `messagingTemplate` directly) is unrelated to and unaffected by the new `/topic/couple/{id}/notifications` push from `NotificationService` — both fire for a match event, on two different topics, and the frontend must listen to both (match-celebration modal vs. notification bell/dropdown) per US-011.
  - This codebase's match tests use `MediaType`/`MatchLike`/`MediaTrack` mocks per-test rather than shared fixtures — when adding a new collaborator (NotificationService) to a service under test, every existing `new MatchService(...)` constructor call site in the test class must be updated, not just one.
  - Same sandbox limitation as all prior stories: no JDK/Maven available (`java`/`mvn` missing, `./mvnw` cannot reach Maven Central) — could not run `./mvnw test` to verify compilation/pass. Code changes are minimal and mirror the existing tested MatchService/MatchServiceTest structure; verify on a machine with JDK 21 + Maven Central access before merging if this matters.
