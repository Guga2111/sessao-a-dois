### JPA / transacoes
- `spring.jpa.open-in-view=false` (Epico 2). A sessao do Hibernate fecha no fim do metodo `@Transactional`, nao no fim da request. Qualquer acesso LAZY fora de transacao lanca `LazyInitializationException` em vez de fazer query extra silenciosa.

### Gotcha #3 deste epico: CookieCsrfTokenRepository + Xor handler quebra CSRF de SPA (US-008)
- `XorCsrfTokenRequestAttributeHandler` (o handler "recomendado" em muitos exemplos genericos do Spring Security) e ERRADO para CSRF via cookie de SPA: o cookie `XSRF-TOKEN` sempre guarda o valor CRU (e o que `CookieCsrfTokenRepository` persiste, independente do handler), e o JS le esse cookie cru e devolve ele cru no header `X-XSRF-TOKEN` - nunca passa por um campo de formulario mascarado. O Xor handler tenta decodificar esse valor cru como se fosse mascarado e o corrompe, derrubando toda requisicao mutante com 403 mesmo com o token certo.
- Um `SpaCsrfTokenRequestHandler` customizado (mascara em `handle()`, resolve cru no header) - o padrao que a documentacao oficial do Spring Security realmente recomenda para SPA - tambem quebrou: `SecurityMockMvcRequestPostProcessors.csrf()` (usado pelos ~47 call sites de teste) obtem o valor do header lendo o que `handle()` colocou no request attribute, entao com `handle()` mascarando, o helper de teste manda um header mascarado, e nosso resolver (que so aceita cru) rejeita de novo.
- Fix que funcionou: handler PURO `new CsrfTokenRequestAttributeHandler()` (sem Xor, sem classe customizada) para `csrfTokenRequestHandler`. Sem mascara em lugar nenhum, cookie cru == header cru == o que `.with(csrf())` gera. BREACH (a razao do Xor existir) nao se aplica aqui porque o token ja e exposto sem mascara no cookie nao-HttpOnly, e este backend nunca reflete o token numa pagina HTML comprimida.
- Detalhe completo em `api/CLAUDE.md` (`com.app.security`, paragrafo CSRF). Se uma story futura mexer em CSRF/SecurityConfig, NAO reintroduza `XorCsrfTokenRequestAttributeHandler` "por seguranca" sem reler esse paragrafo.

### jjwt 0.12.6 (com.app.security) - API de builder/parser
- Emitir iss/aud: `Jwts.builder().subject(...).issuer(issuer).audience().single(audience). ... .signWith(key).compact()` - `.audience()` devolve um `AudienceCollection` cujo `.single(String)` seta um unico valor de audience e retorna o builder de volta (nao precisa de `.and()`).
- Validar iss/aud no parse: `Jwts.parser().verifyWith(key).requireIssuer(issuer).requireAudience(audience).build().parseSignedClaims(token)`. Um valor de iss ou aud errado lanca `io.jsonwebtoken.IncorrectClaimException` (subclasse de `InvalidClaimException`/`JwtException`), distinto de `ExpiredJwtException`/`SignatureException`/`MalformedJwtException` ja tratados.
- Relevante para US-005 (filtro), US-006 (refresh/rotacao) e US-009 (handshake do WebSocket) - todos re-emitem ou re-parseiam tokens via `JwtService`, que agora exige `Duration accessTokenTtl`, `String issuer` e `String audience` no construtor (antes so `long expirationDays`). Qualquer teste que faz `new JwtService(secret, ...)` direto (sem contexto Spring) precisa dos 4 argumentos.

## 2026-08-04 - US-006

- `RefreshTokenService.rotate(rawToken, userAgent, ip)` (com.app.auth): valida o hash do token apresentado, revoga-o (`revokedAt` + `replacedById`) e emite um novo par via o mesmo gerador interno de `issue` (extraido para `issueToken`, que agora retorna raw+entidade para que `replacedById` possa apontar pro id gerado client-side). TTL sempre `now + app.auth.refresh-token-ttl` (deslizante, decisao E5) - nunca herda o vencimento do token que substitui. Devolve `RotationResult(userId, refreshToken)`; quem gera o access token e `AuthService.refresh`, chamando `jwtService.generateToken(rotation.userId())` - `RefreshTokenService` continua sem depender de `JwtService`.
- Deteccao de reuso: token ja revogado por padrao derruba a familia inteira (`revokeFamily`, com `log.warn` citando userId e IP - nunca o token/hash) e lanca `RefreshReuseDetectedException` (401). Excecao: se a revogacao aconteceu ha menos de `app.auth.refresh-reuse-grace` (default `30s`, decisao E4), em vez de punir o servidor segue `replacedById` e rotaciona o token que substituiu o apresentado (loop bounded por `MAX_REUSE_CHAIN_HOPS=10`, defensivo contra dado corrompido) - a familia NAO e revogada nesse caso. Um token expirado mas nunca revogado lanca soh `InvalidRefreshTokenException` (401) sem tocar na familia - expiracao natural nao e sinal de roubo.
