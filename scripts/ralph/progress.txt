## Codebase Patterns

- **O backend AGORA compila e roda testes neste sandbox.** O devcontainer traz Temurin
  JDK 21 + Maven 3.9.16 e o `init-firewall.sh` libera `repo.maven.apache.org` /
  `repo1.maven.org` (commit `0b6d627`, 2026-08-02). Rode `cd api && ./mvnw test`.
  NUNCA dê uma story de backend por concluída sem isso. Se falhar por rede, reexecute
  `sudo /usr/local/bin/init-firewall.sh` (o Maven Central fica atrás de CDN com IPs
  rotativos) antes de concluir qualquer coisa.
  Esta linha SUBSTITUI a antiga "this sandbox has no java/mvn", que era verdadeira até
  2026-08-02. Foi ela que levou o épico Flyway a entregar 7 stories verificadas só por
  análise estática — seguidas de 5 commits de correção manual, incluindo uma dependência
  `spring-boot-flyway` ausente que um único `./mvnw compile` teria pego.

- Ainda ausentes no sandbox: `docker` e `psql`. Sem testcontainers e sem Postgres real —
  por isso o datasource de teste é H2 em `MODE=PostgreSQL`. O CI (`.github/workflows/`)
  roda contra Postgres 17 de verdade, então uma migration que passa aqui ainda pode
  quebrar lá por sintaxe Postgres-only.

- O schema é gerido por **Flyway** desde 2026-08-01 (`api/src/main/resources/db/migration/V*.sql`),
  com `spring.jpa.hibernate.ddl-auto=validate`. Hibernate nunca altera o schema. Toda
  mudança estrutural entra como migration nova — ver `api/CLAUDE.md` para as convenções
  (UUID sem default no banco, `Instant` vs `LocalDateTime`, compatibilidade com H2).

- O skill `/ralph` (`.claude/skills/ralph/SKILL.md`) grava o `prd.json` convertido no
  PRÓPRIO diretório do skill (`.claude/skills/ralph/`), que NÃO é o diretório lido pelo
  loop (`scripts/ralph/`, conforme `scripts/ralph/CLAUDE.md`). Se `scripts/ralph/prd.json`
  aparecer vazio depois de rodar `/ralph`, procure o conteúdo real em
  `.claude/skills/ralph/prd.json` antes de concluir que o PRD não está pronto.

- Ao concluir um épico, **arquive** `prd.json` + `progress.txt` em
  `scripts/ralph/archive/YYYY-MM-DD-<nome>/` antes de começar o próximo. É convenção
  estabelecida (6 épicos arquivados até agora) e o histórico do Flyway quase se perdeu
  por não ter sido arquivado na hora.

- O backlog técnico pós-MVP vive em **`POST-MVP-TASK.md`** na raiz: 35 tasks em 8 épicos,
  cada uma já com arquivo/linha, proposta, critérios de aceite e escopo negativo — ou
  seja, praticamente prontas para virar PRD. As decisões **D1..D12** no topo do arquivo
  são vinculantes; não reabra nenhuma sem registrar o motivo lá.

- **O skill `/ralph` grava em `.claude/skills/ralph/prd.json`, não em `scripts/ralph/prd.json`
  (lido pelo loop).** Confirmado de novo neste épico: rodei `/ralph` e precisei copiar
  manualmente o resultado para `scripts/ralph/prd.json` depois. Sempre espelhar os dois
  arquivos a cada mudança de `passes`/`notes`, ou o próximo `ralph.sh` roda contra um
  prd.json desatualizado.

## 2026-08-02 - US-001
- Implementado fail-fast do `JWT_SECRET` em `JwtService` (construtor): lança
  `IllegalStateException` (mensagem pt-BR citando `JWT_SECRET`) para segredo nulo/branco,
  igual ao antigo default de dev (`dev-only-secret-please-override-in-prod-32bytes+`), ou
  com menos de 32 bytes UTF-8. `api/src/main/resources/application.properties` não declara
  mais default (`app.jwt.secret=${JWT_SECRET:}`).
- Arquivos alterados: `api/src/main/java/com/app/security/JwtService.java`,
  `api/src/main/resources/application.properties`, `docker-compose-dev.yml` (efeito
  colateral, ver abaixo), `api/src/test/java/com/app/security/JwtServiceTest.java` (novo).
- **Learnings for future iterations:**
  - `docker-compose-dev.yml` setava `JWT_SECRET` exatamente igual ao antigo default de dev
    banido pela nova validação — o `docker compose up` local quebraria silenciosamente sem
    esse ajuste. Trocado para `local-dev-compose-secret-not-for-prod-32bytes+` (46 bytes).
    Ao endurecer qualquer validação de config, sempre `grep` por todo o repo (não só
    `api/src/main/resources/`) por valores que a nova regra passaria a rejeitar —
    `docker-compose-dev.yml`, `.env.example`, `docker-compose-prod.yml`, `.github/workflows/`.
  - Os segredos de teste (`test-only-secret-please-override-in-prod-32bytes+`, 49 bytes) e
    de CI (`ci-only-secret-please-override-in-prod-32bytes+`, 47 bytes) já eram válidos
    contra a nova regra (>=32 bytes, diferentes do default banido) — nada a mudar neles,
    conforme a nota de atenção do PRD.
  - Criei `JwtServiceTest.java` só com os 4 cenários de validação do construtor (nulo/branco,
    default banido, curto, válido). A US-003 (`JwtServiceTest` para comportamento de token)
    deve **adicionar** métodos a este mesmo arquivo, não criar um novo — o PRD já avisa que
    os testes de construtor não devem ser duplicados lá.
  - `./mvnw test`: 269/269 passam. Uma falha transitória em
    `MediaTrackRepositoryTest.queriesAreScopedByCoupleIdAndNeverLeakOtherCouplesData` (colisão
    aleatória de `invite_code` único) apareceu numa rodada e sumiu ao re-rodar isolado —
    pré-existente, não relacionada a esta story, não investigada mais a fundo.

## 2026-08-02 - US-002
- Excluída `UserDetailsServiceAutoConfiguration` do auto-config do Spring Boot via
  `@SpringBootApplication(exclude = UserDetailsServiceAutoConfiguration.class)` em
  `SessaoADoisApplication.java`.
- Arquivos alterados: `api/src/main/java/com/app/SessaoADoisApplication.java`.
- **Learnings for future iterations:**
  - **No Spring Boot 4.1.0 (o parent deste projeto), o auto-config de segurança foi
    extraído do `spring-boot-autoconfigure` para um artefato próprio, `spring-boot-security`.**
    `UserDetailsServiceAutoConfiguration` mudou de pacote:
    `org.springframework.boot.security.autoconfigure.UserDetailsServiceAutoConfiguration`,
    NÃO `org.springframework.boot.autoconfigure.security.servlet.*` (que é onde estava em
    Spring Boot 3.x e onde a maioria dos exemplos/docs antigos ainda apontam — esse pacote
    simplesmente não existe mais no jar `spring-boot-autoconfigure-4.1.0.jar`, compilação
    falha com "package does not exist"). Ao usar qualquer classe `*AutoConfiguration`
    relacionada a segurança/actuator neste projeto, primeiro confira o pacote real dentro do
    jar (`unzip -l ~/.m2/repository/org/springframework/boot/spring-boot-security/4.1.0/*.jar`)
    em vez de assumir o pacote do Spring Boot 3.x.
  - Não foi preciso declarar nenhum bean `AuthenticationManager`/`UserDetailsService` vazio —
    excluir a auto-config basta, já que `SecurityConfig` já define seu próprio
    `SecurityFilterChain` com `httpBasic().disable()` e um `JwtAuthenticationFilter` próprio,
    sem depender de um `UserDetailsService` em lugar nenhum.
  - Verificação de que a senha gerada sumiu: `grep -c "Using generated security password"`
    no output completo de `./mvnw test` → 0 matches (antes da mudança essa linha aparecia a
    cada contexto Spring completo subido, ou seja, em todo `@SpringBootTest`).
  - `./mvnw test`: 269/269 passam, nenhuma mudança de comportamento em rotas públicas/privadas
    (os testes de controller que já cobrem 401 sem token continuam verdes).
