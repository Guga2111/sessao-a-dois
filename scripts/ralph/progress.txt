## Codebase Patterns
- Backend package-by-feature under `com.app.<feature>` (see docs/ARCHITECTURE.md); exception handlers use `@RestControllerAdvice(basePackages = "com.app.<feature>")` returning `Map<String,String>`/`Map<String,Object>` bodies (see com.app.auth.AuthExceptionHandler).
- `src/test/resources/application.properties` REPLACES `src/main/resources/application.properties` entirely for `@SpringBootTest` — it does NOT layer on top. It must redeclare every property any eagerly-instantiated bean needs (`tmdb.api-key` for TmdbConfig, `app.jwt.secret` for JwtService, `app.jwt.expiration-days` for JwtService). Adding a new required property to main application.properties means mirroring it in the test one too.
- This sandbox has no JDK/Maven installed and no Maven Central access — `./mvnw test`/`package` cannot be executed; code must be reviewed carefully by hand.
- `couple_id` must always be extracted from the authenticated user's context (SecurityContext → UserDetails → User entity → couple.id), never from the request body, to prevent cross-couple data access.
- All tracking endpoints require JWT (anyRequest().authenticated() in SecurityConfig) — no explicit permitAll needed for /api/tracking/**.
- com.app.media.MediaType enum (MOVIE, TV) already exists from Épico 3 — reuse it in com.app.tracking entities; do not redefine it.
- This codebase's existing entities (User, Couple) store raw UUID FK fields, not JPA relations — com.app.tracking.MediaTrack/UserReview are the first to use @ManyToOne/@OneToMany; follow that relation-based style within com.app.tracking since the PRD calls for it there specifically.
- spring.jpa.hibernate.ddl-auto=update was already set in application.properties before Épico 4 — no change needed for new entities to get their tables created.
- MediaTrackResponse.reviews always has exactly 2 slots (one per couple member), built from Couple.user1Id/user2Id, NOT from however many UserReview rows exist — MediaTrackService.toResponse() (package-visible, reused by UserReviewService in US-003) looks up each member's User by id for userName and matches an existing UserReview by user id for rating/opinion (null if absent).

## [2026-07-21] - US-005

- **Learnings for future iterations:**
  - `Couple`/`User` entities have `@GeneratedValue` ids with no setter — when a unit test needs a non-null id (e.g. to make `findOwnedTrack`'s `track.getCouple().getId().equals(coupleId)` check pass, or to make `MediaTrackService.toReviewDto`'s `review.getUser().getId().equals(memberId)` not NPE), construct the entity normally then set the id with `org.springframework.test.util.ReflectionTestUtils.setField(entity, "id", someUuid)`. Forgetting this on a `User` passed into `MediaTrackService.addTrack` causes a real `NullPointerException` inside `toResponse`/`toReviewDto`, not a clean assertion failure — the plain "new User(...)" has a null id by default.
  - `UserReviewService.upsertReview`'s update-existing-review branch mutates the review already returned by `userReviewRepository.findByMediaTrackIdAndUserId` in place and does NOT touch `track.getReviews()` — only the create-new-review branch appends to that in-memory list (matches the earlier US-003 learning). Tests asserting on `track.getReviews()` size must account for this asymmetry.
  - `@WebMvcTest(SomeController.class)` auto-registers same-package `@RestControllerAdvice` beans (e.g. `TrackingExceptionHandler`) without an explicit `@Import` — confirmed by mirroring `CoupleControllerTest`'s working pattern; only `SecurityConfig` needs an explicit `@Import` for the JWT filter chain to apply.
