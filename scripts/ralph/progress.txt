## Codebase Patterns
- `client/`: dark theme prototype colors are historically inlined via Tailwind arbitrary values (`bg-[#161513]`, etc.) — see `client/CLAUDE.md`. As of Epico 13/US-001, `client/src/index.css` now carries the *real* brand palette as semantic tokens (`.dark` block), so future color-migration stories (US-003+) should map hex -> token per the list in that file's comment, not invent new arbitrary values.
- The app is dark-only in practice (D17, `POST-MVP-TASK.md`): the `ThemeProvider`/`d`-key toggle to light mode still exists in code but produces a broken UI, since every screen hardcodes dark hex regardless of theme. Removing that toggle is a separate future story (T13.3) — don't touch `:root` (light) tokens for color-migration work, only `.dark`.
- Hex/oklch round-trip check: convert with the standard sRGB<->OKLCH matrices (D65, CSS Color 4), round L/C/H to 3 decimals, then convert back and diff per-channel — 1 unit of rounding tolerance is expected and acceptable.
- `bun run typecheck`/`lint`/`test:run`/`build` are all run from `client/` (that's where `package.json` lives), not the repo root.

## 2026-08-13 - US-001
- Implemented: `client/src/index.css`'s `.dark` block now declares the app's real brand palette as semantic tokens, replacing 6 of the generic shadcn neutral defaults and adding 1 new token, so future migration stories can replace hardcoded hex/arbitrary-value classNames with token utilities instead of copy-pasted hex.
  - `--background` -> `#09090a` (oklch(0.14 0.002 286.109))
  - `--foreground` -> `#f6f4ec` (oklch(0.966 0.011 95.163))
  - `--card` -> `#161513` (oklch(0.196 0.004 84.591))
  - `--primary` -> `#ffcb2b` (oklch(0.864 0.167 88.652))
  - `--muted-foreground` -> `#a6a39a` (oklch(0.715 0.013 91.563))
  - `--destructive` -> `#ff6b6b` (oklch(0.712 0.181 22.839))
  - `--accent` (reused, was unused by any component/primitive) -> `#ffe08a` (oklch(0.914 0.111 90.281)) — "destaque claro" (light accent: hover state of the primary yellow, highlighted links/text)
  - `--destructive-foreground` (NEW token, also added to the `@theme inline` block as `--color-destructive-foreground`) -> `#ffb3b3` (oklch(0.839 0.089 19.107)) — light-red text used over translucent destructive-tinted surfaces (error banners, "Tentar novamente" chips). None of the 8 reusable semantics (`--background`/`--card`/`--foreground`/`--muted-foreground`/`--primary`/`--destructive`/`--accent`/`--popover`) represent "light text on a destructive wash", so a new token was the only option — named `--destructive-foreground` to match the existing shadcn `--primary`/`--primary-foreground` pairing convention.
  - `:root` (light theme) intentionally left untouched — see Codebase Patterns above (D17).
  - `--card-foreground`, `--popover`, `--popover-foreground`, `--accent-foreground`, `--primary-foreground` left untouched: not among the 8 required hexes, no evidence they need to change for this story's scope, and touching them would only add risk without an AC requiring it.
- Files changed: `client/src/index.css` only (no `.tsx` touched, per AC).
- Verification: `bun run typecheck` / `bun run lint` / `bun run test:run` (119 tests, 14 files, all green) / `bun run build` all pass from `client/`.
- Hex->oklch round-trip (AC requirement): computed with a standalone Node script using the CSS Color 4 sRGB<->OKLCH matrices; every one of the 8 tokens round-trips within 1 unit per channel (7 of 8 exact, `#ffcb2b` round-trips to `#ffcb2c`, 1 unit off on the blue channel).
- **Known nuance surfaced during implementation (documented for the human gate, not blocking):** the AC's premise "nenhum componente usa os tokens ainda, entao redefinir token nao move pixel" is true for every `.tsx` screen file (100% of ~70 `<Button>` usages found across `screens/`/`components/`/`routes/` were checked and each one overrides background/text color via an arbitrary hex className, which `cn()`/`twMerge` resolves in favor of the arbitrary value over the token-driven variant class) — but it is **not strictly true** for a few `components/ui/` primitives that already consume `--primary`/`--destructive`/`--foreground` directly: `button.tsx`'s `default`/`link`/`destructive` variants (`bg-primary`, `text-primary-foreground`, `text-primary`, `bg-destructive/10`, focus-visible/aria-invalid destructive states) and `outline` variant's `hover:text-foreground`/`aria-expanded:text-foreground`. These only render their *un-overridden* pixels in interaction states (hover/focus-visible/aria-expanded/aria-invalid) that a static screenshot wouldn't normally catch, since every actual usage site overrides the base background/text color in its own `className`. No default-static-render pixel diff was found. Flagging this explicitly per D19 (gate humano, `POST-MVP-TASK.md`) since visual verification isn't possible in this sandbox (no browser) — a human should spot-check hover/focus states on a `Button` with `variant="destructive"` (e.g. `SuggestionsTab.tsx`'s reject button) and any `variant="link"`/default-variant button before merge.
