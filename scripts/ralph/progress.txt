- **Learnings for future iterations:**
  - Reduced-motion pattern used here (reusable for US-009's animated dashboard bars): give every animated element's *base* (non-prefixed) Tailwind classes the final/settled visual state (e.g. `opacity-100`), then add the actual CSS animation only via `motion-safe:animate-[keyframeName_Ns_ease_infinite]`. Under `prefers-reduced-motion: reduce`, the `motion-safe:` utility simply never applies (Tailwind wraps it in `@media (prefers-reduced-motion: no-preference)`), so the element renders its static final state automatically — no separate reduced-motion branch or JS media-query check needed.
  - For a multi-element synced CSS loop (multiple pieces of UI animating in relation to each other), define one shared keyframes duration (here 6s) and give each element's `@keyframes` percentage stops that line up on that same timeline, rather than juggling separate `animation-delay`s per element — much easier to reason about and keeps everything visually in sync since they all start at mount.

- **Learnings for future iterations:**
  - `react-hooks/set-state-in-effect` only flags `setState` called *synchronously in the effect body itself* — calling `setState` inside an `IntersectionObserver` callback (or any other async/event callback) registered from within `useEffect` is fine, since the callback fires later, outside the effect's synchronous execution. This is the clean way to do scroll/viewport-triggered reveals without the `key`-remount workaround documented in `client/CLAUDE.md`.
  - Reduced-motion pattern for a *one-shot scroll reveal* (as opposed to MatchShowcase's *looping* animation): keep the animated value driven by React state (e.g. bar `width` via inline `style`), but only apply the CSS transition itself via `motion-safe:transition-[...]`. Under `prefers-reduced-motion: reduce` the transition class never applies, so the value still changes when state flips (0% -> target%) but snaps instantly instead of animating — satisfies "renders final state statically", no separate reduced-motion branch needed. Complements (doesn't replace) the `motion-safe:animate-[...]` pattern from US-008 which is for infinite/looping CSS keyframes rather than state-driven one-shot transitions.
