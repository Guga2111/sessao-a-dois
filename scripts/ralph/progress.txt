## Codebase Patterns

- **`bun` is installable in this sandbox via `npm install -g bun`** (registry.npmjs.org is
  firewall-allowlisted; `bun.sh` itself, used by the official install script, is NOT
  reachable — `curl -fsSL https://bun.sh/install` fails with connection refused). Any
  story that needs `bun run ...` verified for real (not just read statically) should use
  this instead of assuming bun is unavailable.
- **`client/package.json`'s `typecheck` script was silently broken before US-011:**
  `"typecheck": "tsc --noEmit"` ran against the root `tsconfig.json`, which has
  `"files": []` and only `references` to `tsconfig.app.json`/`tsconfig.node.json` — without
  `-b` (build mode), plain `tsc` on a references-only root config type-checks **zero
  files** and always exits 0, even with a real type error in `src/`. Fixed to
  `"typecheck": "tsc -b"` (same as the `build` script's first half, which already worked
  correctly because `-b` follows project references). Confirmed with a deliberate
  `const x: number = "a string"` in `src/main.tsx`: old script → exit 0 (silent pass), new
  script → exit 2 with the real error. If a future story touches `typecheck`/`build`
  scripts or `tsconfig*.json`, re-verify with a deliberate error rather than trusting a
  clean run — a no-op script produces a clean run too.
- `bun run lint` (`eslint .`) currently reflects the **real** state of the codebase, no
  known false-positives left as of US-011 — if it fails, something is actually wrong.

- **O backend AGORA compila e roda testes neste sandbox.** O devcontainer traz Temurin
  JDK 21 + Maven 3.9.16 e o `init-firewall.sh` libera `repo.maven.apache.org` /
  `repo1.maven.org` (commit `0b6d627`, 2026-08-02). Rode `cd api && ./mvnw test`.
  NUNCA dê uma story de backend por concluída sem isso. Se falhar por rede, reexecute
  `sudo /usr/local/bin/init-firewall.sh` (o Maven Central fica atrás de CDN com IPs
  rotativos) antes de concluir qualquer coisa.
  Esta linha SUBSTITUI a antiga "this sandbox has no java/mvn", que era verdadeira até
  2026-08-02. Foi ela que levou o épico Flyway a entregar 7 stories verificadas só por
  análise estática — seguidas de 5 commits de correção manual, incluindo uma dependência
  `spring-boot-flyway` ausente que um único `./mvnw compile` teria pego.

- Ainda ausentes no sandbox: `docker` e `psql`. Sem testcontainers e sem Postgres real —
  por isso o datasource de teste é H2 em `MODE=PostgreSQL`. O CI (`.github/workflows/`)
  roda contra Postgres 17 de verdade, então uma migration que passa aqui ainda pode
  quebrar lá por sintaxe Postgres-only.

- O schema é gerido por **Flyway** desde 2026-08-01 (`api/src/main/resources/db/migration/V*.sql`),
  com `spring.jpa.hibernate.ddl-auto=validate`. Hibernate nunca altera o schema. Toda
  mudança estrutural entra como migration nova — ver `api/CLAUDE.md` para as convenções
  (UUID sem default no banco, `Instant` vs `LocalDateTime`, compatibilidade com H2).

- O skill `/ralph` (`.claude/skills/ralph/SKILL.md`) grava o `prd.json` convertido no
  PRÓPRIO diretório do skill (`.claude/skills/ralph/`), que NÃO é o diretório lido pelo
  loop (`scripts/ralph/`, conforme `scripts/ralph/CLAUDE.md`). Se `scripts/ralph/prd.json`
  aparecer vazio depois de rodar `/ralph`, procure o conteúdo real em
  `.claude/skills/ralph/prd.json` antes de concluir que o PRD não está pronto.

- Ao concluir um épico, **arquive** `prd.json` + `progress.txt` em
  `scripts/ralph/archive/YYYY-MM-DD-<nome>/` antes de começar o próximo. É convenção
  estabelecida (6 épicos arquivados até agora) e o histórico do Flyway quase se perdeu

- O backlog técnico pós-MVP vive em **`POST-MVP-TASK.md`** na raiz: 35 tasks em 8 épicos,
  cada uma já com arquivo/linha, proposta, critérios de aceite e escopo negativo — ou

## 2026-08-02 - US-002
- Excluída `UserDetailsServiceAutoConfiguration` do auto-config do Spring Boot via
  `@SpringBootApplication(exclude = UserDetailsServiceAutoConfiguration.class)` em
  `SessaoADoisApplication.java`.
- Arquivos alterados: `api/src/main/java/com/app/SessaoADoisApplication.java`.
- **Learnings for future iterations:**
  - **No Spring Boot 4.1.0 (o parent deste projeto), o auto-config de segurança foi
    extraído do `spring-boot-autoconfigure` para um artefato próprio, `spring-boot-security`.**
    `UserDetailsServiceAutoConfiguration` mudou de pacote:
    `org.springframework.boot.security.autoconfigure.UserDetailsServiceAutoConfiguration`,
    NÃO `org.springframework.boot.autoconfigure.security.servlet.*` (que é onde estava em
    Spring Boot 3.x e onde a maioria dos exemplos/docs antigos ainda apontam — esse pacote
    simplesmente não existe mais no jar `spring-boot-autoconfigure-4.1.0.jar`, compilação
    falha com "package does not exist"). Ao usar qualquer classe `*AutoConfiguration`
    relacionada a segurança/actuator neste projeto, primeiro confira o pacote real dentro do
    jar (`unzip -l ~/.m2/repository/org/springframework/boot/spring-boot-security/4.1.0/*.jar`)
    em vez de assumir o pacote do Spring Boot 3.x.
  - Não foi preciso declarar nenhum bean `AuthenticationManager`/`UserDetailsService` vazio —
    excluir a auto-config basta, já que `SecurityConfig` já define seu próprio
    `SecurityFilterChain` com `httpBasic().disable()` e um `JwtAuthenticationFilter` próprio,
    sem depender de um `UserDetailsService` em lugar nenhum.
  - Verificação de que a senha gerada sumiu: `grep -c "Using generated security password"`
    no output completo de `./mvnw test` → 0 matches (antes da mudança essa linha aparecia a
    cada contexto Spring completo subido, ou seja, em todo `@SpringBootTest`).
  - `./mvnw test`: 269/269 passam, nenhuma mudança de comportamento em rotas públicas/privadas
    (os testes de controller que já cobrem 401 sem token continuam verdes).

## 2026-08-02 - US-003
- Adicionados 5 métodos de teste a `JwtServiceTest.java` (mesmo arquivo da US-001, sem
  duplicar os testes de construtor): round-trip generateToken/parseSubject, token expirado
  (ExpiredJwtException), token assinado com outra chave (SignatureException), subject que

- Arquivos alterados: `api/src/test/java/com/app/security/JwtServiceTest.java`.
- **Learnings for future iterations:**
  - `JwtService` não expõe a `SecretKey` interna nem aceita um clock injetável. Para testar
    cenários que `generateToken` não permite construir diretamente (token já expirado,
    subject não-UUID), o teste recria a mesma chave com

    `JwtService` com outro segredo válido (`OTHER_VALID_SECRET`, 40 bytes) e usar seu
    `generateToken` normal - não precisa montar o JWT na mão.
  - jjwt 0.12.6: `Jwts.parser().verifyWith(key).build().parseSignedClaims(token)` lança
    `io.jsonwebtoken.security.SignatureException` para assinatura inválida,
    `io.jsonwebtoken.ExpiredJwtException` para expiração, e
    `io.jsonwebtoken.MalformedJwtException` para string que não é um JWT válido - todas
    subclasses de `JwtException`, nenhuma NPE mesmo com entrada arbitrária.

  `/api/couple/me`, `/api/notifications` sem token -> 401.
- Arquivos alterados: `api/src/test/java/com/app/security/SecurityConfigTest.java` (novo).
- **Learnings for future iterations:**
  - **Spring Boot 4.1.0 moveu `@AutoConfigureMockMvc` para
    `org.springframework.boot.webmvc.test.autoconfigure`** (artefato `spring-boot-webmvc-test`),
    não `org.springframework.boot.test.autoconfigure.web.servlet` (pacote do Spring Boot 3.x,
    que não existe mais aqui — mesma família de mudança já registrada em `api/CLAUDE.md` para
    `UserDetailsServiceAutoConfiguration`). O mesmo pacote novo já hospeda `@WebMvcTest`
    (confirmado em `AuthControllerTest.java`, que já importava de lá). Ao usar qualquer
    anotação de teste do Spring Boot que "sempre" morou em
    `org.springframework.boot.test.autoconfigure.*`, primeiro confirme o pacote real via
    `unzip -l` no jar `spring-boot-webmvc-test-4.1.0.jar` (ou o artefato de teste equivalente)
    em vez de assumir a doc/exemplos do Spring Boot 3.x.
  - Para testar 401 de uma rota privada por falta de token, **não é preciso mockar nada** — a
    rejeição acontece no `JwtAuthenticationFilter`/`authorizeHttpRequests`, antes de qualquer
    controller/service rodar, então mesmo endpoints que chamariam TMDB real (`/api/media/search`)
    ou exigiriam parâmetros de query nunca chegam lá; um `GET` simples sem header já basta.
  - Para o teste de `POST /api/auth/login` retornando 200, usar credenciais **reais** (registrar
    o usuário no mesmo teste antes de logar) em vez de tentar contornar a validação: login com
    email/senha errados passa por `InvalidCredentialsException`, que `AuthExceptionHandler`
    também mapeia para 401 — isso mascararia a diferença entre "bloqueado pelo Spring Security"
    (o que a story testa) e "rejeitado pela regra de negócio do AuthService".
  - Como o teste roda com contexto completo e DB real (H2 `create-drop`, sem `@Transactional`),
    dados gravados por um método de teste persistem para os demais métodos da mesma classe
    (mesmo contexto Spring é reutilizado) — usar e-mails únicos por `UUID.randomUUID()` em
    qualquer teste de integração que registre usuários, para não colidir com
    `EmailAlreadyExistsException` entre métodos.

- **Learnings for future iterations:**
  - `JwtHandshakeInterceptor` não tem dependências para mockar além de `JwtService` — usei a
    instância real (mesmo padrão de `JwtServiceTest`: `VALID_SECRET`/`OTHER_VALID_SECRET`)
    em vez de `Mockito.mock(JwtService.class)`, porque gerar tokens reais válidos/inválidos é
    mais simples e mais fiel do que stubar `parseSubject`.
  - Para exercitar o parsing real feito por `extractToken` (que faz
    `UriComponentsBuilder.fromUri(((ServletServerHttpRequest) request).getURI())`), construí
    o `ServerHttpRequest` com `new ServletServerHttpRequest(new MockHttpServletRequest("GET",

    diretamente — o cast `instanceof ServletServerHttpRequest` no código de produção exige um
    objeto real dessa classe, um mock genérico de `ServerHttpRequest` falharia nesse cast.
  - **Descoberta importante, útil para qualquer teste futuro envolvendo query params via
    `UriComponentsBuilder.fromUri(uri).build()`:** essa combinação NÃO decodifica
    percent-encoding — `token=%20` chega em `getQueryParams()` como a string literal `"%20"`

    scratch test isolado (classpath direto do `spring-web` do `.m2`) antes de escrever o
    teste real. Por isso o caso "vazio ou em branco" do PRD foi coberto só com `token=`
    (valor vazio, que produz `String` vazia de verdade, `isBlank() == true`) — um valor
    `%20` testaria na prática o branch de "token malformado" (JWT inválido), não o branch de
    `isBlank()`, e duplicaria semanticamente o teste de token malformado.
  - `Mockito.verifyNoInteractions(response)` confirma que o caminho de sucesso não toca no
    `ServerHttpResponse` (só o de rejeição chama `setStatusCode(UNAUTHORIZED)`).
  - `./mvnw test`: 287/287 passam (282 pré-existentes + 5 novos).

  `/topic/**` e `/app/**`), já que só mensagens SUBSCRIBE batem no
  `simpSubscribeDestMatchers`. Bean `csrfChannelInterceptor` (nome exato) sobrescrito como
  no-op para não exigir um token CSRF que o client atual não envia.
- Arquivos alterados: `api/pom.xml`,
  `api/src/main/java/com/app/websocket/WebSocketSecurityConfig.java` (novo),
  `api/src/test/java/com/app/websocket/WebSocketSecurityConfigTest.java` (novo).
- **Learnings for future iterations:**
  - **Antes de começar esta story, encontrei o trabalho da US-006 já implementado
    (`CoupleDestinationAuthorizationManager` + teste) e marcado `passes: true` no
    `prd.json`, mas nunca commitado nem registrado em `progress.txt`** — sinal de uma
    iteração anterior interrompida antes do passo de commit. Terminei esse commit primeiro
    (com testes reverificados) antes de iniciar esta story. Sempre rodar `git status`
    contra o `prd.json` no início de uma iteração para pegar esse tipo de trabalho órfão.
  - `@EnableWebSocketSecurity` (pacote `org.springframework.security.config.annotation.web.socket`,
    não mudou de local nesta versão) registra automaticamente um `AuthorizationChannelInterceptor`
    no `clientInboundChannel` a partir de **qualquer bean único do tipo
    `AuthorizationManager<Message<?>>`** no contexto — não é preciso injetar nada manualmente
    em `WebSocketConfig`, só declarar o bean numa `@Configuration` separada.
  - `MessageMatcherDelegatingAuthorizationManager.Builder.Constraint` não tem um método
    `.custom(...)` explícito — para plugar uma regra própria (em vez de `hasRole`/`permitAll`/
    `denyAll`), use `.access(AuthorizationManager<MessageAuthorizationContext<?>>)`. O
    `MessageAuthorizationContext` só expõe `getMessage()`/`getVariables()`; para pegar destino
    e atributos de sessão STOMP a partir da mensagem, use
    `SimpMessageHeaderAccessor.wrap(message).getDestination()`/`.getSessionAttributes()`.
  - **Descoberta chave sobre `simpSubscribeDestMatchers`:** ele só bate em mensagens do tipo
    STOMP `SUBSCRIBE`, então um `SEND` direto do cliente para `/topic/couple/{id}/match`
    (tentando forjar uma publicação) nunca casa com esse matcher e cai automaticamente no
    `anyMessage().denyAll()` — nenhuma regra extra foi necessária para bloquear "SEND direto
    pra qualquer destino", só o próprio deny-by-default.
  - **`anyMessage().denyAll()` bloquearia até o frame `CONNECT`** (e DISCONNECT/UNSUBSCRIBE/
    HEARTBEAT) se eles não fossem explicitamente liberados antes com
    `.simpTypeMatchers(SimpMessageType.CONNECT, ...).permitAll()` — sem isso o handshake
    SockJS/STOMP quebraria por completo assim que o client tentasse conectar, mesmo com JWT
    válido no handshake HTTP. Isso não está óbvio na documentação do Spring Security sobre
    `@EnableWebSocketSecurity`, só aparece ao ler o bytecode de
    `WebSocketMessageBrokerSecurityConfiguration` (`ANY_MESSAGE_AUTHENTICATED` como fallback
    interno não cobre isso da forma que a US-007 pede - deny, não authenticated).
  - O nome literal do bean CSRF (`"csrfChannelInterceptor"`) foi confirmado via
    `strings`/bytecode de `WebSocketMessageBrokerSecurityConfiguration.class`
    (`~/.m2/repository/org/springframework/security/spring-security-config/7.1.0/...jar`),
    não só por lembrança da doc do Spring Security 5/6 — vale conferir assim de novo se uma
    versão futura do Spring Security renomear a constante.
  - `SimpMessagingTemplate.convertAndSend(...)` (usado por `MatchService`/
    `NotificationService` para push do servidor) escreve no `clientOutboundChannel`, não no
    `clientInboundChannel` onde o `AuthorizationChannelInterceptor` é registrado — por isso
    nenhuma mudança foi necessária nesses dois arquivos, e os testes existentes
    (`MatchServiceTest`/`NotificationServiceTest`) continuam verdes sem tocar neles.
  - Para testar a autorização de mensagens STOMP **sem** subir um WebSocket real: injete o
    bean `@Qualifier("clientInboundChannel") MessageChannel` num `@SpringBootTest`, construa
    a mensagem com `StompHeaderAccessor.create(StompCommand.SUBSCRIBE/SEND/CONNECT)` +
    `MessageBuilder.createMessage(payload, accessor.getMessageHeaders())`, e chame
    `channel.send(message)` diretamente — os `ChannelInterceptor`s (incluindo o de
    autorização) rodam de forma síncrona dentro do `send()`. Uma rejeição não lança
    `AccessDeniedException` diretamente do `send()` — o Spring Messaging embrulha em
    `MessageDeliveryException`, então o teste precisa checar `.hasCauseInstanceOf(AccessDeniedException.class)`,
    não `.isInstanceOf(...)`.
  - `./mvnw test`: 300/300 passam (293 pré-existentes + 7 novos).
