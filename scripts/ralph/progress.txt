## Codebase Patterns
- ResourceNotFoundException now lives in com.app.common (moved from com.app.tracking in US-001). Any class in another package that throws/catches it must `import com.app.common.ResourceNotFoundException;` explicitly - it is no longer implicitly available within com.app.tracking either, since the package changed.
- Backend test suite: `./mvnw -o test` from `api/` (offline mode works in this sandbox). 421 tests total as of US-002. Some tests deliberately log ERROR/exception stacktraces as part of asserting error-handling behavior (e.g. MediaControllerTest's TMDB-unavailable case, MatchService.healMetadata) - that noisy output is expected and not a failure signal; check the final "Tests run: X, Failures: 0, Errors: 0" summary instead.
- **@RestControllerAdvice ordering gotcha (US-002):** a feature `*ExceptionHandler` with NO explicit `@Order` defaults to `Ordered.LOWEST_PRECEDENCE` (same as `Integer.MAX_VALUE`). If a global catch-all advice (`@ExceptionHandler(Exception.class)`) is ALSO set to `Ordered.LOWEST_PRECEDENCE` (the naive "make it run last" choice), the two tie and Spring's exception resolution is NOT "most specific match wins across all advices" - it's "first advice bean (by order, ties broken by discovery order) that has ANY matching handler (including via Exception.class through the hierarchy) wins". With a tie, the global catch-all can end up being checked before a feature handler, silently swallowing e.g. `CoupleAlreadyFullException` as a generic 500. Fix: every feature `*ExceptionHandler` needs an explicit `@Order(Ordered.HIGHEST_PRECEDENCE)` so it's unambiguously checked before the global `@Order(Ordered.LOWEST_PRECEDENCE)` advice. Any NEW feature exception handler added later must also get `@Order(Ordered.HIGHEST_PRECEDENCE)` or it will silently lose to `GlobalExceptionHandler`'s `Exception.class` fallback.
- **Test-only support classes for a specific test (US-002):** a `@RestController`/`@Component` that exists ONLY to be exercised by one test (e.g. a controller with endpoints that deliberately throw each exception type `GlobalExceptionHandler` handles) must live under `src/test/java`, never `src/main/java` - putting it in `src/main` registers it as a real endpoint in production. Package-private visibility (no `public`) is enough since the test class lives in the same package.
- `@WebMvcTest(SomeController.class)` auto-discovers ALL `@RestControllerAdvice`/`@ControllerAdvice` beans on the classpath regardless of the `controllers` argument (unlike `@Controller`, which IS restricted to what's listed) - this is why `GlobalExceptionHandlerTest` needed a `@MockitoBean JwtService` (pulled in transitively via `SecurityConfig` -> `JwtAuthenticationFilter`) even though its own support controller has nothing to do with JWTs.
- **Facade/port pattern for cross-feature entity creation (US-003):** when feature A needs to create an entity owned by feature B, add a narrow `@Service` "facade"/"port" class inside feature B's package (e.g. `com.app.tracking.TrackingFacade`) exposing only the specific operations A needs (by domain params, not by leaking the repository or the entity class), and have A depend on that facade instead of B's repository/entity/enum classes directly. This keeps A's imports free of B's internals so a future refactor of B's entity doesn't ripple into A. When writing a Mockito test for the caller (A), replace direct repository-save `ArgumentCaptor<Entity>` assertions with `verify(facade).theMethod(eq(...), eq(...), argCaptor.capture())` and assert on the DTO/params passed in - the facade's OWN unit test (or a small parity test) is where entity-field assertions belong.
