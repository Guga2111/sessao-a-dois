# Backend (api/)

Spring Boot (parent 4.1.0) + Java 21, built with the Maven wrapper `./mvnw`.

## Conventions
- **Base Java package is `com.app`** (e.g. `com.app.SessaoADoisApplication`). Do NOT use the old `com.lf.sessao_a_dois`.
- **Maven `groupId` stays `com.lf`** — this is intentional and separate from the Java package. Do not "align" them.
- **Package-by-feature** is the target structure: `com.app.user`, `com.app.couple`, `com.app.media`, `com.app.tracking`, `com.app.match`, `com.app.security`, `com.app.websocket` (see `docs/ARCHITECTURE.md`).
- Testing stack: JUnit 5 + Mockito (+ spring-security-test); Controllers, Services and Repositories require coverage.
- **Spring Boot 4.1.0 moved security auto-configuration out of `spring-boot-autoconfigure` into its own artifact, `spring-boot-security`.** Classes like `UserDetailsServiceAutoConfiguration` now live under `org.springframework.boot.security.autoconfigure.*`, not `org.springframework.boot.autoconfigure.security.servlet.*` (the Spring Boot 3.x package, which no longer exists in this project's `spring-boot-autoconfigure-4.1.0.jar`). When referencing any `*AutoConfiguration` class for security/actuator, verify the real package first (`unzip -l ~/.m2/repository/org/springframework/boot/spring-boot-security/4.1.0/*.jar | grep ClassName`) instead of assuming Spring Boot 3.x docs/examples.
- **Schema/Flyway:** production runs the real `api/src/main/resources/db/migration/V*__*.sql` files via Flyway (`spring.flyway.locations=classpath:db/migration`) with Hibernate `ddl-auto=validate` — Hibernate never mutates the schema there. **Dev/test does NOT go through the same path**: `api/src/test/resources/application.properties` sets `spring.flyway.enabled=false` and `spring.jpa.hibernate.ddl-auto=create-drop`, so every `@DataJpaTest`/`@SpringBootTest` slice gets a schema generated directly from the JPA entities, not from the migration files (this is deliberate — `@DataJpaTest` forces a plain H2 without `MODE=PostgreSQL` via `PropertyMappingContextCustomizer`, which is incompatible with the migrations' Postgres syntax regardless of what `spring.test.database.replace` is set to). The one exception is `com.app.migration.FlywayMigrationTest` (`@SpringBootTest`, not `@DataJpaTest`, `@AutoConfigureTestDatabase(replace = NONE)`), which overrides `spring.flyway.enabled=true` + `ddl-auto=validate` and points `spring.datasource.url` at `jdbc:h2:mem:migrations;MODE=PostgreSQL;DATABASE_TO_LOWER=TRUE` (or `${DB_URL}` when set, which is how CI runs it against the real `postgres:17-alpine` service) — this is the only test that actually applies V1/V2/... in sequence and validates entities against the resulting schema; if you add a migration and only see it exercised by static reading, it hasn't really been verified. All `@Id` fields across entities use `@GeneratedValue(strategy = GenerationType.UUID)`, i.e. Hibernate generates the UUID client-side before insert — migrations must NOT give `id` columns a DB-side default (no `gen_random_uuid()`/`DEFAULT`), that would just be dead code the app never relies on. `Instant`-typed columns (e.g. `created_at` on `User`/`Couple`) map to `TIMESTAMP WITH TIME ZONE`; `LocalDateTime`-typed columns (e.g. `created_at` on `MediaTrack`/`MatchLike`/`MatchReject`, via `@CreationTimestamp`) map to plain `TIMESTAMP` — don't use the two interchangeably when writing a new migration for an entity with a timestamp column.
- **`com.app.security` (JWT):** `JwtService` is constructed with `app.jwt.secret`, `app.jwt.access-token-ttl` (`Duration`, default `15m`), `app.jwt.issuer` and `app.jwt.audience` — any test that instantiates it directly (not via `@MockitoBean`) needs all 4 constructor args, in that order. Uses jjwt 0.12.6's newer builder/parser API: emit `iss`/`aud` with `Jwts.builder().issuer(issuer).audience().single(audience)` (`.single(String)` sets one audience value and returns the builder, no `.and()` needed); validate them on parse with `Jwts.parser().requireIssuer(issuer).requireAudience(audience)` — a mismatch throws `io.jsonwebtoken.IncorrectClaimException`, not `SignatureException`/`MalformedJwtException`. `validateSecret` (blank/dev-default/<32 bytes) is orthogonal to this and runs before any of it.
  - **`JwtAuthenticationFilter` (Epico 4, US-005) reads the access token from the `access_token` cookie, not the `Authorization` header** — `WebUtils.getCookie(request, AuthCookieService.ACCESS_TOKEN_COOKIE)`, guarded by `StringUtils.hasText(cookie.getValue())` so a present-but-blank cookie takes the same "not authenticated" path as a missing one instead of reaching `JwtService.parseSubject` with an empty string. There is no header fallback (decision D1 — direct cutover, ~8 known users, no transition window); do not reintroduce one. Any future code that needs to read the same cookie (refresh rotation, WebSocket handshake) should use the same `WebUtils.getCookie` + `AuthCookieService.ACCESS_TOKEN_COOKIE` pattern rather than hand-rolling cookie lookup.
  - **CSRF (Epico 4, US-008) uses `CookieCsrfTokenRepository.withHttpOnlyFalse()` with a PLAIN `CsrfTokenRequestAttributeHandler`, deliberately NOT `XorCsrfTokenRequestAttributeHandler`.** This is a documented Spring Security gotcha for cookie-based SPA CSRF: the `XSRF-TOKEN` cookie always holds the raw token (that's what `CookieCsrfTokenRepository` persists regardless of handler), and this app's JS reads that raw cookie value and echoes it verbatim in the `X-XSRF-TOKEN` header — it never goes through a server-rendered form field. The Xor handler's `resolveCsrfTokenValue` assumes the submitted value is XOR-masked (the form-field scenario) and corrupts a raw value on decode, so every mutating request would fail with 403 even with the "right" token — this bit a first implementation attempt and is easy to reintroduce by copy-pasting the "recommended" Xor handler from generic Spring Security docs/examples without checking they're for the cookie-SPA case specifically. A custom `SpaCsrfTokenRequestHandler` (mask for `handle()`, raw for `resolveCsrfTokenValue()`) was tried as the "correct" fix per Spring's own SPA guide, but it broke every `SecurityMockMvcRequestPostProcessors.csrf()` call site across the controller tests, because that test helper populates the header from whatever `handle()` put in the request attribute (masked) — so with a masking `handle()`, the helper sends a masked header while our plain resolver expects raw, a second 403. The plain (non-Xor) handler avoids both problems, and loses no real protection here since BREACH mitigation (the reason Xor masking exists) only matters when the token is reflected into a compressible server-rendered HTML response, which this JSON API + non-HttpOnly-cookie design never does. `CookieCsrfTokenRepository` only saves the cookie when `CsrfToken#getToken()` is actually read, which `CsrfFilter` only forces on state-changing methods — a `CsrfCookieFilter` (`OncePerRequestFilter`, registered `addFilterAfter(..., BasicAuthenticationFilter.class)`) forces that read on every request so a GET-only bootstrap (e.g. `GET /api/auth/me`) still gets the cookie before the first POST needs it. Ignored routes (`ignoringRequestMatchers`): `/api/auth/login`, `/api/auth/register`, `/api/health`, `/api/auth/refresh`, `/api/auth/logout` — the last two by design (decision E6), since they must work before the client necessarily has a valid CSRF token yet.
- **`com.app.media` (TMDB integration):** `TmdbConfig` exposes a single `RestClient` bean (`tmdbRestClient`) that fails fast (`IllegalStateException`) if `tmdb.api-key` (env `TMDB_API_KEY`) is blank — the bean is eagerly instantiated, so this happens at context startup. Default `language=pt-BR` is injected on every outgoing request via a `ClientHttpRequestInterceptor` (`TmdbDefaultLanguageInterceptor`) that wraps the request with `HttpRequestWrapper` to rewrite the URI — this is the pattern to follow for any other default query param the TMDB client needs.
  - **`src/test/resources/application.properties` REPLACES `src/main/resources/application.properties` entirely for `@SpringBootTest`, it does not layer on top of it.** Spring Boot only loads one `application.properties` per classpath root, and `test-classes` wins over `classes`. This file must therefore redeclare every property any eagerly-instantiated bean needs (currently `tmdb.api-key` for `TmdbConfig` and `app.jwt.secret` for `JwtService`) — adding a new required property to the main file without mirroring it here will silently break `SessaoADoisApplicationTests.contextLoads` and any other full-context test.
  - Raw TMDB JSON responses are mapped to package-private Java records (e.g. `TmdbMultiSearchItem`) with `@JsonProperty`/`@JsonIgnoreProperties(ignoreUnknown = true)`, then translated into a public simplified DTO (`MediaSearchResult`) — never expose the raw TMDB shape past the service layer.
  - `MediaPage` (public record: `results`, `page`, `totalResults`, `totalPages`) is the shared paginated-response DTO for any `com.app.media` endpoint backed by a paged TMDB list (trending, discover, and eventually search). `GET /trending/all/week` returns items in the same shape as `/search/multi`, so `MediaSearchService.trending(page)` reuses `TmdbMultiSearchItem` for the per-item mapping (via `TmdbTrendingResponse`, which only adds `page`/`total_pages`/`total_results`) instead of declaring a parallel item record — do the same for any other TMDB list endpoint with that shape. `MediaPage`'s compact constructor clamps `totalPages`/`totalResults` to the TMDB cap (500 pages × 20 = 10000) whenever the upstream response reports more — this applies automatically to every call site that builds a `MediaPage` (no per-endpoint clamping needed).
  - `GET /api/media/discover` (`MediaSearchService.discover(DiscoverFilters)`) calls `/discover/movie` and/or `/discover/tv`. That item shape differs from `/search/multi`/`/trending/all/week` (no `media_type`, but includes `popularity`), so it has its own `TmdbDiscoverItem`/`TmdbDiscoverResponse` records instead of reusing `TmdbMultiSearchItem` — the `MediaType` must be passed in explicitly when mapping a `TmdbDiscoverItem` to `MediaSearchResult`, since the item itself doesn't carry it. `DiscoverFilters.mediaType() == null` means "both movie and tv" (`MediaType.fromQueryValueOrNull` turns a blank/absent query param into `null`, reusing `fromPathValue`'s validation/exception for a non-blank invalid value). When `mediaType` is `null`, both endpoints are called for the *same* requested page, their items are merged with a comparator matching the requested `DiscoverSortBy`, then sliced to 20 — `totalResults` is the sum of both TMDB responses' totals, `totalPages` is `ceil(totalResults / 20.0)`. `DiscoverSortBy` resolves `release_date.desc/asc` to `primary_release_date.*` (movie) or `first_air_date.*` (tv) via `tmdbValue(MediaType)`, since TMDB has no single "release date" sort field shared by both endpoints. `releaseDecades` (CSV of decade-start years, e.g. `"2020,2000"`) always collapses to a single min–max date range (`min(decades)-01-01` .. `(max(decades)+9)-12-31`) — decades in the middle of a non-contiguous selection are intentionally included, per product decision. `DiscoverFilters.certifications()` (CSV of BR certification chips, e.g. `"Livre,16,18"`) is resolved by `MediaSearchService.certificationCeilingFor` to a single TMDB ceiling: `"Livre"` maps to `"L"`, unknown chips are silently dropped, and when multiple valid chips are given the *highest* (most restrictive, per `CERTIFICATION_ORDER = [L,10,12,14,16,18]`) is used as `certification.lte` (TMDB's `.lte` semantics already include everything more permissive). This is only applied to `/discover/movie` calls — `/discover/tv` never receives `certification_country`/`certification`, since TMDB doesn't support certification filtering for TV — so any code branching on `mediaType == MediaType.MOVIE` inside `callDiscover` is where this and any other movie-only TMDB param belongs.
  - `GET /api/media/genres` (`MediaSearchService.genres()`) calls `/genre/movie/list` and `/genre/tv/list` (mapped via the new `TmdbGenreListResponse` record, `{genres: [TmdbGenre...]}`) and merges both lists into `List<MediaGenre>` (the public `id`/`name` DTO), deduplicating by `name()` with a `LinkedHashMap` (`putIfAbsent`, movie genres inserted first) — this is the pattern for merging two same-shaped TMDB list endpoints into one deduplicated public list, distinct from the `discoverBoth` merge-by-sort-comparator pattern used for paginated results.
  - To assert the exact query params/path a service builds for a TMDB call (not just the response mapping), capture the `Function<UriBuilder, URI>` passed to `.uri(...)` with `ArgumentCaptor<Function<UriBuilder, URI>> captor = ArgumentCaptor.forClass(Function.class)` (needs `@SuppressWarnings("unchecked")`), call `captor.getValue().apply(UriComponentsBuilder.newInstance())` to get the built `URI`, then inspect it with `UriComponentsBuilder.fromUri(uri).build().getQueryParams()` — reuse this for any future test that needs to verify TMDB URL construction rather than just the mocked response.
  - Endpoints in `com.app.media` inherit `anyRequest().authenticated()` from `SecurityConfig` (no explicit `permitAll()` added) — media search/details require a JWT like the rest of the app.
  - To unit-test a service that calls the shared `RestClient` bean, mock it with `Mockito.mock(RestClient.class, RETURNS_DEEP_STUBS)` and stub the terminal `.body(SomeType.class)` call — the fluent `get().uri(...).retrieve()` chain is otherwise painful to mock directly.
  - Entities with `@GeneratedValue` ids (`User`, `Couple`, `MediaTrack`, ...) have no id setter. In a plain Mockito unit test, `new User(...)`/`new Couple(...)` always has a null id, which silently breaks any code comparing ids (e.g. ownership checks, or NPEs on `review.getUser().getId().equals(x)`). Use `org.springframework.test.util.ReflectionTestUtils.setField(entity, "id", someUuid)` to give a test entity the id it needs.
  - TMDB call failures (5xx, 4xx other than a handled 404, timeouts/connection errors) are caught with `catch (RestClientResponseException | ResourceAccessException ex)` around the `tmdbRestClient` call and rethrown as `TmdbUnavailableException`, which `MediaExceptionHandler` maps to `502 Bad Gateway` with a generic pt-BR message (never leaking the TMDB URL, stacktrace, or API key). When a narrower exception (e.g. `HttpClientErrorException.NotFound` → 404) is also caught in the same method, its `catch` clause must come **before** the generic `RestClientResponseException` one, since it's a subclass. To simulate a TMDB 5xx in tests, build one with `HttpServerErrorException.create(HttpStatus, String, HttpHeaders, byte[], Charset)`.
  - `MediaDetails.genreIds()` (raw TMDB genre ids, separate from `genres()` which is already-translated pt-BR names) is how any feature outside `com.app.media` should obtain genre ids — never re-parse `TmdbGenre` outside this package. `MediaTrack.genreIds` (`@ElementCollection` → `media_track_genre` table) is populated from it whenever a track is created (`MediaTrackService.addTrack`, `MatchService.createMatch`). Callers that must not fail track creation on a flaky TMDB (`MediaTrackService`) wrap the `mediaDetailsService.getDetails(...)` call in `catch (RuntimeException)` and fall back to an empty list — this is the pattern to reuse for any other "enrich from TMDB, but don't block persistence" need.
  - **`com.app.notification`:** For match/no-match events, `actor_user_id` is the `userId` of whichever `MatchService.like()`/`reject()` call is the one that triggers the event (closes the match, or diverges from the partner's like) — not necessarily the first user to act. `NotificationService.notifyCouple(couple, type, tmdbId, mediaType, title, actorUserId)` is the single entry point for creating notifications — it persists one `Notification` per couple member (`couple.getUser1Id()`/`getUser2Id()`, skipping null) and returns their DTOs. Any feature that must notify a couple (match, no-match, future events) should call this from inside its own `@Transactional` method rather than building `Notification`/STOMP sends by hand. The STOMP push to `/topic/couple/{coupleId}/notifications` (one message per notification DTO) is deferred via `TransactionSynchronizationManager.registerSynchronization(...)`'s `afterCommit()` hook when a transaction is active, so the row is guaranteed to exist in the DB before the client receives the push — falls back to sending immediately if no transaction is active. `NotificationDto` is a record serialized both by the REST endpoints and by the STOMP push, so adding a component changes the wire shape for both at once — and breaks every positional `new NotificationDto(...)` (grep before touching). `NotificationService.notifyRatingRequest(couple, recipientUserId, actorUserId, tmdbId, mediaType, title, mediaTrackId)` is the second entry point, for single-recipient events: it persists exactly one `Notification` (type `RATING_REQUEST`) for `recipientUserId`, returns `Optional<NotificationDto>`, and returns `Optional.empty()` without persisting or pushing when `recipientUserId` is null (couple with no partner yet). It shares the same `scheduleBroadcast` after-commit path as `notifyCouple`. `Notification` carries a nullable `media_track_id` used only by `RATING_REQUEST`; its 7-arg constructor delegates to the 8-arg one with `null`, which is the pattern to follow when adding an optional field so existing callers (`MatchService`) stay untouched. Schema changes now go through Flyway (`spring.jpa.hibernate.ddl-auto=validate` — Hibernate never mutates the schema): add a new versioned file under `api/src/main/resources/db/migration/` (e.g. `V3__...sql`), do not rely on Hibernate auto-DDL for new columns/tables. This is the pattern to reuse for any other "persist then push after commit" need (the existing `MatchService.createMatch` STOMP send is NOT after-commit and predates this pattern).
  - **`MediaTrackMapper` (com.app.tracking)** is the only place that turns a `MediaTrack` into a `MediaTrackResponse`. It takes the couple's member names as an already-resolved `Map<UUID, String>` parameter and does **not** inject `UserRepository` — resolving that map (one `userRepository.findAllById(memberIds)` call) is the caller's job, same pattern as `NotificationService.resolveActorNames`. `MediaTrackMapper.memberIds(Couple)` is the shared static helper for "this couple's non-null member ids" (skips a null `user2Id`), used both to build the map and inside the mapper's per-review loop. Every `MediaTrackService`/`UserReviewService` method that returns a `MediaTrackResponse` (or a list/page of them) must resolve names **once per request** — for a list/page, collect the distinct member ids across all tracks first (they're normally all the same couple, but don't assume it) and do a single `findAllById`, never one lookup per track. `UserReviewService` depends on `MediaTrackMapper` directly, not on `MediaTrackService` — do not reintroduce that dependency (it was removed specifically to break a bidirectional coupling between the two services).
  - **`spring.jpa.open-in-view=false`** (main and test `application.properties`, US-004): the Hibernate session closes at the end of each `@Transactional` service method, not at the end of the HTTP request. Any code that returns an entity (or something holding one) from a non-`@Transactional` method and then touches a LAZY association afterwards will throw `LazyInitializationException` instead of silently doing an extra query — every mutator in `MediaTrackService`/`UserReviewService` that calls `resolveMemberNames(...)`/`mediaTrackMapper.toResponse(...)` must be `@Transactional` (this is why `startWatching` got the annotation in US-004: it was the one mutator missing it). `MediaTrackRepository.findByCoupleId`/`findByCoupleIdAndStatus`/`findByIdIn` carry `@EntityGraph(attributePaths = {"reviews", "reviews.user", "couple"})` to fetch those associations in the same query instead of relying on the (now gone) OSIV window. The paginated finder does NOT use `@EntityGraph` directly: combining a collection fetch join with `Pageable` makes Hibernate paginate in memory (`HHH000104`), so `MediaTrackService.listByStatusPaged` instead pages over `findIdsByCoupleIdAndStatusOrderByCreatedAtDesc` (id-only projection, no fetch join, real DB pagination) and then loads that page's rows via `findByIdIn` (entity graph, no `Pageable`) — reorder the `IN` result by the id list afterward, since SQL `IN` doesn't preserve order. `MediaTrackQueryCountTest` is the pattern for proving this kind of fix isn't just a static read: it enables Hibernate `Statistics` on the real `EntityManagerFactory` (`entityManagerFactory.unwrap(SessionFactory.class).getStatistics()`) and compares `getPrepareStatementCount()` for a small vs. large track count through a real `MockMvc` request (asserting equality proves the query count doesn't scale with N), and attaches a Logback `ListAppender` to the root logger to assert no `HHH000104` message was emitted during the paginated request. **Self-heal pattern for pre-V4 rows (US-005):** `MediaTrackService.healMetadata(MediaTrack)` and `MatchService.healMetadata(MatchLike)` are private methods called at the top of a read path (`listByStatus`/`listByStatusPaged`, `MatchService.getPending`) — when `title == null` they fetch `mediaDetailsService.getDetails(...)` once, set `title`/`posterUrl`/`releaseYear`, and `save(...)` the entity so every later read skips TMDB for that row; a `catch (RuntimeException)` leaves the fields null (retried next read) instead of failing the request. Every caller of a `healMetadata` method must be `@Transactional` for the same OSIV reason as above. This logic lives in the service, never in `MediaTrackMapper` — replicate the same two-method (heal + the read method that calls it) shape for any other entity that needs the same treatment, rather than centralizing it in the mapper or in a shared helper across packages.
  - **`RatingRequestService` (com.app.tracking)** is the single orchestrator for the RATING_REQUEST flow: `onRatingRegistered(track, actorUserId)` is called at the end of every path that records a rating (`MediaTrackService.markAsWatched`, `MediaTrackService.addTrack` when the new track is `WATCHED`, and `UserReviewService.upsertReview`), inside the caller's transaction — those three methods are `@Transactional` precisely so the notification row and the after-commit STOMP push line up with the rating write. Never notify from a new call site by hand; add the call to the orchestrator instead. It no-ops when the actor has no rating, the couple has no partner, the partner already has a rating, or an unread RATING_REQUEST already exists for `(recipient, couple, tmdbId)` — that last check is `NotificationRepository.existsByRecipientUserIdAndCoupleIdAndTmdbIdAndTypeAndReadFalse`, always scoped by couple so two couples tracking the same `tmdbId` never interfere. The notification title comes from `MediaDetailsService.getDetails(...).title()` wrapped in `catch (RuntimeException)` with the `RatingRequestService.FALLBACK_TITLE` fallback — a flaky TMDB must never fail the rating write. The same orchestrator also *resolves* the actor's own pending requests: before deciding whether to notify the partner, it marks every unread `RATING_REQUEST` for `(actor, couple, tmdbId)` as read (`NotificationRepository.findByRecipientUserIdAndCoupleIdAndTmdbIdAndTypeAndReadFalse` + `saveAll`), so rating a title through any of the three paths clears the bell badge without a manual click.
  - **Aggregation queries for dashboard-style stats** live as `@Query`-annotated methods directly on the relevant repository (`MediaTrackRepository`, `UserReviewRepository`), always scoped with `WHERE ... .couple.id = :coupleId` (never trust a caller-supplied couple id from anywhere but the JWT). Group-by queries return a `List<SomeProjection>` where `SomeProjection` is a small nested interface (`getX()`/`getY()` matching the JPQL aliases) declared inside the repository — Spring Data's interface-based projections bind by alias name, not by position, so the `AS alias` in the `SELECT` must match the getter name (`AS genreId` → `getGenreId()`). `SUM`/`COUNT` aggregates that could return `NULL` (e.g. `SUM` over zero matching rows) are wrapped in `COALESCE(..., 0)` in the JPQL rather than handled with nullable `Integer` in Java. Month/year grouping uses standard JPQL `EXTRACT(MONTH FROM ...)` / `EXTRACT(YEAR FROM ...)` (portable across the H2 test datasource and PostgreSQL), not native SQL or Hibernate's `month()`/`year()` HQL extensions.
  - **`StatsService` (com.app.tracking)** composes the `MediaTrackRepository`/`UserReviewRepository` aggregation queries above into a single `StatsResponse` DTO for the dashboard — it does not query entities directly, only the existing aggregate queries, so adding a new stat should mean adding a new repository aggregate first. `GenreNames` is a package-private static `Map<Integer, String>` (TMDB movie + tv genre ids merged, pt-BR names) used to resolve `genre_id` → display name; ids with no entry are silently dropped rather than shown as `null`/blank. Percentages and the average rating are rounded to 1 decimal with a shared `round1` helper (`Math.round(value * 10.0) / 10.0`) — reuse that rounding approach for any new percentage/rating field rather than `String.format` or `BigDecimal`. Monthly series are always zero-filled for all 12 months of the current year (not just months with data) so the frontend can render a fixed-width chart without gap-filling itself. A couple with no `WATCHED` titles must produce a fully zeroed/empty `StatsResponse`, never throw — `UserReviewRepository.findAverageRatingByCoupleIdAndMediaTrackStatus` returning `null` is the main source of NPEs to guard against here. `StatsService.emptyStats()` builds the same zero/empty shape for the "user has no couple yet" case (distinct from "couple has no watched titles"); `MediaTrackController.stats()` (`GET /api/tracking/stats`) is the only endpoint in this controller that does NOT use the shared `currentCoupleId(userId)` helper — that helper throws `ResourceNotFoundException` (404) when the user has no couple, but the stats endpoint's contract is 200 + empty state instead, so it checks `coupleService.getCurrentCouple(userId)` directly and branches to `emptyStats()`.

- **`com.app.auth` (Epico 4 - migracao de autenticacao) in one paragraph:** the session is two HttpOnly cookies (`access_token`, 15 min TTL; `refresh_token`, 30-day sliding TTL, `Path=/api/auth/refresh`), built/cleared exclusively through `AuthCookieService` — never construct a `ResponseCookie` by hand anywhere else. `RefreshToken` (the entity behind `refresh_token`) stores ONLY the SHA-256 hash of the token value, never the raw value — there is no code path anywhere that recovers the original token from the database, so a leaked DB row alone doesn't give an attacker a working session. Reuse detection has a 30s grace window (`app.auth.refresh-reuse-grace`, decision E4): presenting an already-revoked token within 30s of its revocation is treated as a legitimate race between two tabs rotating concurrently (rotates the substitute instead of punishing), while a reuse outside that window revokes the whole token family. **Any new property under `app.jwt.*`/`app.auth.*` must be mirrored in `api/src/test/resources/application.properties`** — that file replaces (not merges with) the main one for every `@SpringBootTest`, so a property only declared in the main file silently breaks `SessaoADoisApplicationTests.contextLoads` (see the Schema/Flyway note above for the general mechanism). See the more detailed per-class notes below for `AuthCookieService`, `RefreshTokenService.rotate`, and `JwtAuthenticationFilter`/`JwtHandshakeInterceptor`.
- **`AuthController.sessionResponse(User)`** (Epico 4, US-004) is the single place that builds the `{user, couple}` `LoginResponse` shape shared by `POST /api/auth/login` and `GET /api/auth/me` — any future endpoint in `com.app.auth` that needs to describe "the current session" must call it instead of re-assembling `UserSummary`/`CoupleResponse` a third time (the existing duplication of that assembly logic against `CoupleController` is a separate, already-tracked issue and must not grow). `GET /api/auth/me` returns 200 with `couple: null` (never 404) when the authenticated user has no couple yet — this is deliberately different from `GET /api/couple/me`, which 404s in that case; `/me` under `com.app.auth` is the bootstrap-safe one.
- **`com.app.auth.AuthCookieService`** (Epico 4, US-003) is the only place that builds the session `ResponseCookie`s (`access_token` Path=`/`, `refresh_token` Path=`/api/auth/refresh`) — any endpoint that sets or clears them (login, refresh-rotation, logout) must go through it instead of building `ResponseCookie` by hand, so the HttpOnly/Secure/SameSite/Path flags can't drift between call sites. Multiple `Set-Cookie` headers on one response are added with two separate `.header(HttpHeaders.SET_COOKIE, cookie.toString())` calls on the same `ResponseEntity.BodyBuilder` (not a single call with two values) — `HttpHeaders` is a multi-value map, so each call appends rather than overwriting. To assert on them in a `MockMvc` test, read `result.getResponse().getHeaders(HttpHeaders.SET_COOKIE)` (a `List<String>`) and match by the `name=` prefix, since `ResponseCookie#toString()` doesn't expose its flags as separate MockMvc `cookie()` matchers cover (e.g. `SameSite`).
  - **`expiredAccessTokenCookie()`/`expiredRefreshTokenCookie()`** (Epico 4, US-007) build the `Max-Age=0` clearing cookies for `POST /api/auth/logout`, reusing the same `build(name, value, path, maxAge)` private helper with `Duration.ZERO` — this is why a cookie is only actually cleared browser-side when the clearing `Set-Cookie` uses the exact same `Path` as the original: a different Path creates a second, unrelated cookie instead of overwriting the first. `RefreshTokenService.revoke(rawToken)` (distinct from `revokeFamily`, which nukes every active token for a user) revokes only the single presented token and is intentionally idempotent — unknown or already-revoked token is a silent no-op, not an exception, since logout's contract is "this token doesn't work anymore," which is already true in both cases.
- **`RefreshTokenService.rotate(rawToken, userAgent, ip)`** (Epico 4, US-006) is the only place that rotates a refresh token: it revokes the presented token (`revokedAt` + `replacedById`) and issues a fresh one with a sliding TTL (`now + app.auth.refresh-token-ttl`, never inherited from the token it replaces), returning `RotationResult(userId, refreshToken)` — the caller (`AuthService.refresh`) mints the paired access token via `JwtService.generateToken(rotation.userId())`, `RefreshTokenService` itself never touches JWTs. Reuse detection: presenting an already-revoked token normally revokes the whole family (`revokeFamily`, logged with `log.warn(userId, ip)` — never the token/hash) and throws `RefreshReuseDetectedException`; but if that token was revoked less than `app.auth.refresh-reuse-grace` (default `30s`) ago — decision E4, for two tabs racing a refresh — it instead follows `replacedById` and rotates *that* token instead (chained, bounded by `MAX_REUSE_CHAIN_HOPS`), since the raw value of the substitute can never be recovered from the DB (US-001) and re-rotating is the only way to hand the caller a working pair without punishing a legitimate race. An expired-but-never-revoked token throws the plain `InvalidRefreshTokenException` (401) without touching the family — natural expiry isn't a theft signal. Both exceptions are mapped to 401 in `AuthExceptionHandler`; `POST /api/auth/refresh` is `permitAll` in `SecurityConfig` (the access token is expired by definition when this endpoint is called) and reads the `refresh_token` cookie the same way `JwtAuthenticationFilter` reads `access_token` (`WebUtils.getCookie` + `AuthCookieService.REFRESH_TOKEN_COOKIE`, no fallback).
  - To test a `@Value`-driven flag (like `app.auth.cookie.secure`) at two different values inside the same `@WebMvcTest`, use a JUnit 5 `@Nested` class per value with its own `@TestPropertySource(properties = "...")` — Spring Framework's default `@NestedTestConfiguration(INHERIT)` gives each nested class its own cached `ApplicationContext` (keyed by the merged properties) while still inheriting the outer class's `@WebMvcTest`/`@Import`/`@MockitoBean` setup, so the nested test methods can reference the outer class's `mockMvc`/mock fields directly (as an inner class) without redeclaring them.

- **Per-account rate limiting (Epico 5, US-003):** `RateLimitExceededException` (`com.app.security`, carries `retryAfterSeconds`) is thrown directly from service methods (`AuthService.login` for `login:email:<normalized>`, `CoupleService.joinCouple` for `couple-join:user:<userId>`) - both call `RateLimitService.tryConsume` the same way `RateLimitFilter` does, just with an account-scoped key instead of an IP-scoped one, and construct their own `RateLimitProperties.Limit` lookup (`getLoginByEmail()`/`getCoupleJoinByUser()`). Each feature package's own `@RestControllerAdvice` (`AuthExceptionHandler`, `CoupleExceptionHandler`) gets an `@ExceptionHandler(RateLimitExceededException.class)` that returns the same 429 + `Retry-After` header + `{"message": ...}` shape as the filter - `@RestControllerAdvice(basePackages = "com.app.X")` only restricts which *controllers* it advises, not the package of the exception thrown, so this works even though `RateLimitExceededException` itself lives in `com.app.security`. Any future per-account limit (e.g. US-009's regenerate endpoint) should follow this exact shape: compose a key, call `tryConsume`, throw `RateLimitExceededException(result.retryAfterSeconds())` on `!result.allowed()` - do not add a new exception type or a new handler pattern. Tests for this layer construct real `RateLimitService`/`RateLimitProperties` instances (not mocks) since bucket4j has no useful surface to mock - a dedicated small-capacity/short-window `RateLimitProperties.Limit` (e.g. capacity 1, `Duration.ofMillis(150)`) built per-test gives fast, deterministic exceed/release assertions without touching the shared default-limit instance used by the rest of the test class's non-rate-limit assertions.
- **`com.app.security` rate limiting (Epico 5, US-001):** `RateLimitService.tryConsume(String key, int capacity, Duration window)` is the single generic entry point for every rate limit in the app (bucket4j `Bucket.builder().addLimit(Bandwidth.classic(capacity, Refill.intervally(capacity, window)))` per key, cached in a `ConcurrentHashMap` with a `@Scheduled` inactivity sweep) - any new limit (per-IP in a filter, per-account inside a service) should compose its own string key (e.g. `"login:ip:" + ip`, `"login:email:" + normalizedEmail`) and call this same service rather than adding a parallel bucket cache. Defaults/config live in `RateLimitProperties` (`@ConfigurationProperties(prefix = "app.rate-limit")`, a plain `@Component` - this codebase has no `@EnableConfigurationProperties`/`@ConfigurationPropertiesScan`, component scan alone registers it). `ClientIpResolver` (`request.getHeader("X-Forwarded-For")` first entry, else `request.getRemoteAddr()`) is the only IP-resolution logic in the app - `AuthController` uses it via constructor injection; any new controller/filter needing the client IP must reuse it instead of re-deriving. Any `@WebMvcTest` for a controller that depends on `ClientIpResolver` must add `ClientIpResolver.class` to its `@Import({...})` list (plain `@Component`s are not auto-wired into a `@WebMvcTest` slice).
  - **`RateLimitFilter` (Epico 5, US-002)** applies the IP-based limits to `POST /api/auth/login`/`register`/`refresh` and `POST /api/couple/join`, registered via `SecurityConfig.rateLimitFilterRegistration` at `Ordered.HIGHEST_PRECEDENCE` (NOT disabled in the servlet chain, unlike `jwtFilterRegistration`) so a blocked request never reaches Spring Security, BCrypt or the DB. Unlike `ClientIpResolver`/`RateLimitService`/`RateLimitProperties` (plain `@Component`s), `RateLimitFilter` implements `jakarta.servlet.Filter` and is therefore auto-included by every `@WebMvcTest` slice's default scanning — do NOT add it to a test's `@Import({...})` list, only its three constructor dependencies need that. Writing the 429 body directly (not through a Spring MVC message converter) requires the Spring-managed `ObjectMapper` — inject `tools.jackson.databind.ObjectMapper` (Jackson 3, Spring Boot 4.1's framework-managed Jackson), not `com.fasterxml.jackson.databind.ObjectMapper` (Jackson 2 — only on the classpath transitively at runtime via `jjwt-jackson`, not compile scope). Because `RateLimitFilter` is live in every `@WebMvcTest`/`@SpringBootTest` context, `api/src/test/resources/application.properties` sets `app.rate-limit.enabled=false` by default — a test class with several `@Test` methods hitting login/register shares one cached context (and thus one `RateLimitService` singleton keyed by the shared `127.0.0.1` MockMvc IP), so leaving it enabled would trip the default per-minute caps across unrelated tests. A test that needs the filter actually active (`RateLimitFilterTest`) flips it back with `@TestPropertySource(properties = {"app.rate-limit.enabled=true", ...})`, shrinking capacity/window (e.g. `2` / `3s`) so exceed/release assertions run in seconds instead of the real 1-minute/1-hour default windows.
- **`com.app.websocket.JwtHandshakeInterceptor`** (Epico 4, US-009) reads the access token from the `access_token` cookie, not the old `?token=` query param — `WebUtils.getCookie(servletRequest.getServletRequest(), AuthCookieService.ACCESS_TOKEN_COOKIE)` on the `ServletServerHttpRequest` (the handshake's `ServerHttpRequest` isn't a `HttpServletRequest` directly, it wraps one via `getServletRequest()`), guarded by `StringUtils.hasText(...)`. No query-param fallback (same decision D1 as `JwtAuthenticationFilter`/US-005) — a token only in the query string with no cookie is rejected with 401 before any connection opens. `USER_ID_ATTRIBUTE` written into the handshake session attributes is unchanged, so `CoupleDestinationAuthorizationManager`/`WebSocketSecurityConfig` needed no changes.
- **Invite-code lifecycle (Epico 5, US-007):** `Couple.inviteCode` is now nullable (`V6__add_invite_code_expiry.sql` dropped its `NOT NULL`) and `Couple.inviteCodeExpiresAt` (`Instant`, nullable, null = "never expires") was added — the decision (documented in the migration's header comment) is that a used/expired invite is **cleared to `NULL`**, not marked-used in a separate column, since Postgres allows multiple `NULL`s under the existing `UniqueConstraint(invite_code)`. `Couple` keeps its old 2-arg constructor (`user1Id`, `inviteCode`, defaulting `inviteCodeExpiresAt` to `null`) for every existing call site, plus a 3-arg constructor for the TTL wiring. `CoupleProperties` (`com.app.couple`, `@ConfigurationProperties(prefix = "app.couple")`, plain `@Component` like `RateLimitProperties`) exposes `inviteCodeTtl` (default `7d`, env `COUPLE_INVITE_CODE_TTL`). `InviteCodeGenerator.generate()` now always returns exactly 8 characters (`LENGTH = 8`, was a random 6–8 range) — any test asserting a length range on generated codes is stale. `FlywayMigrationTest`'s applied-versions list must include every new migration version as a string (`"6"` was added here) or the test silently stops proving the new file was actually exercised.
- **Invite-code expiry/invalidation (Epico 5, US-008):** `CoupleService.createCouple` now calls the 3-arg `Couple` constructor with `Instant.now().plus(coupleProperties.getInviteCodeTtl())`. `joinCouple` checks `couple.getInviteCodeExpiresAt()` right after the `findByInviteCode` lookup (null = never expires, so legacy rows are unaffected) and throws the new `InviteCodeExpiredException` (`com.app.couple`, mapped to `410 GONE` by `CoupleExceptionHandler`) before the self-join/already-paired/already-full checks — an expired code is invalid regardless of who's using it. On a successful join, `Couple.clearInviteCode()` (new entity method, nulls both `inviteCode` and `inviteCodeExpiresAt`) is called before `save`, so a second attempt with the same code string gets `InviteCodeNotFoundException` (repository lookup by the now-`NULL` code never matches), not a stale `CoupleAlreadyFullException`. `CoupleResponse` gained `inviteCodeExpiresAt` and needs no special-casing to hide `inviteCode` post-pairing — it just reads `couple.getInviteCode()`, which is already `null` once `clearInviteCode()` ran. `CoupleService`'s constructor gained a 5th arg (`CoupleProperties`) — any test/call site constructing it directly needs updating (see `CoupleServiceTest`'s `setUp`/helper pattern).
- **Invite-code regeneration (Epico 5, US-009):** `POST /api/couple/invite-code/regenerate` (`CoupleController.regenerateInviteCode`, authenticated, no request body) calls `CoupleService.regenerateInviteCode(userId)`, which: (1) enforces a per-user rate limit reusing `RateLimitProperties.getCoupleJoinByUser()`'s capacity/window (US-003's infra) but under its own key namespace (`"invite-code-regenerate:user:" + userId`, not `"couple-join:user:"` — a distinct bucket, not a shared one); (2) looks up the caller's couple via `findByUser1IdOrUser2Id`, throwing the new `CoupleNotFoundException` (404) if none; (3) throws the new `NotCoupleCreatorException` (403) if the caller isn't `user1Id`; (4) throws the existing `CoupleAlreadyFullException` (409, reused rather than a new type) if the couple is already paired (`user2Id != null`); (5) otherwise calls the new `Couple.regenerateInviteCode(String, Instant)` mutator (sets both `inviteCode` and `inviteCodeExpiresAt` in one call, unlike `clearInviteCode()` which only nulls) with a fresh `generateUniqueInviteCode()` result and `Instant.now().plus(coupleProperties.getInviteCodeTtl())`, then saves. The old code stops working immediately since it's overwritten, not just left to expire.
- **`com.app.common.PageResponse<T>`** (US-009) is the shared JSON contract for any endpoint that returns a paginated result — `content`/`totalElements`/`totalPages`/`number`/`size`, built with `PageResponse.from(page)`. Services keep returning Spring Data `Page<T>` (that's still the right internal type for `Pageable`/`PageRequest` plumbing); only the controller method converts at the `ResponseEntity` boundary via `PageResponse.from(...)`. Do not use `@EnableSpringDataWebSupport(pageSerializationMode = VIA_DTO)` for this — it nests the metadata under a `page` object and would break the flat shape already mirrored in `client/src/types/*.ts`. Any new paginated endpoint should return `PageResponse<T>`, never `Page<T>`, directly.
- **`CorrelationIdFilter`** (Epico 5, US-011) generates (or reuses, when present) the `X-Request-Id` header into `MDC` key `correlationId` for every request, cleared in a `try/finally` so it never leaks to the next request served by the same pooled Tomcat thread, and echoes the id back on the response via the same header. Registered in `SecurityConfig.correlationIdFilterRegistration` at `Ordered.HIGHEST_PRECEDENCE` — one order slot *before* `RateLimitFilter` (now `HIGHEST_PRECEDENCE + 1`), so every log line emitted by any later filter/service for this request (including a 429 from `RateLimitFilter`, or the audit logger from a future story) already has the correlation id in MDC. `logging.pattern.level=%5p [correlationId=%X{correlationId}]` in `application.properties` appends the MDC value to Spring Boot's default console pattern via the documented `logging.pattern.level` extension point, instead of hand-rolling a full `logging.pattern.console` (or a `logback-spring.xml`, which does not exist yet — reserved for a later story that also needs a file appender). Like `RateLimitFilter`, `CorrelationIdFilter` implements `jakarta.servlet.Filter` and is auto-included by every `@WebMvcTest` slice without needing an explicit `@Import` (it has no constructor dependencies of its own, so no import is needed at all for it).
- **`SecurityAuditLogger`** (`com.app.security`, Epico 5, US-012) is the single place that writes to the dedicated `security.audit` logger (name is a plain string, not a package — configure its level independently via `logging.level.security.audit`, default `INFO` through `SECURITY_AUDIT_LOG_LEVEL`). Every event method (`loginSuccess`/`loginFailure`/`logout`/`refresh`/`refreshReuseDetected`/`coupleCreated`/`coupleJoined`/`inviteCodeRegenerated`/`rateLimitExceeded`) takes only identifiers (user/couple id, email, IP, endpoint path) — NEVER a password, raw/hashed token or invite-code value — and delegates to a private `log(event, fields)` that centralizes the `event=... correlationId=... key="value"...` formatting (reads `CorrelationIdFilter.MDC_KEY` from `MDC` itself, callers don't pass it). Emission points are exactly `AuthService` (login success/failure), `RefreshTokenService` (`revoke`→logout, `performRotation`→refresh, `handleRevokedToken`'s reuse branch→refreshReuseDetected — same spot as the existing `log.warn`), `CoupleService` (`createCouple`/`joinCouple`/`regenerateInviteCode`, logged right after `save()` succeeds) and `RateLimitFilter` (in `writeTooManyRequests`'s caller, once per 429) — do not add a new emission point elsewhere; add a new method to `SecurityAuditLogger` and call it from one of these four instead. `SecurityAuditLogger` has no constructor dependencies, so any unit test that builds `AuthService`/`CoupleService`/`RefreshTokenService` directly (not via Spring) just needs `new SecurityAuditLogger()`; any `@WebMvcTest` importing `RateLimitService`/`RateLimitProperties`/`ClientIpResolver` for `RateLimitFilter` now also needs `SecurityAuditLogger.class` in the same `@Import({...})` list.
- **`api/src/main/resources/logback-spring.xml`** (Epico 5, US-013) persists the `security.audit` logger's output to a file outside the container's writable layer. It deliberately does NOT `<include resource="org/springframework/boot/logging/logback/base.xml"/>` — that legacy resource unconditionally attaches a `FILE` appender writing to `${LOG_PATH:-/tmp}/spring.log`, which would silently change the app's default behavior (console-only today). Instead it includes only `defaults.xml` + `console-appender.xml` and rebuilds the same `<root level="INFO"><appender-ref ref="CONSOLE"/></root>` by hand, so the normal log format/behavior is byte-for-byte what it was before this file existed. The `SECURITY_AUDIT_FILE` appender (a `RollingFileAppender` + `SizeAndTimeBasedRollingPolicy`, the exact same policy class Spring Boot's own `file-appender.xml` uses — `maxFileSize=10MB`, `maxHistory=10`, `totalSizeCap=100MB`) is attached only to the `security.audit` logger (`additivity` defaults to `true`, so it still also reaches `CONSOLE` via root — no `additivity="false"` here, unlike a typical "split this logger into its own file only" setup). Its path comes from `app.security.audit-log.path` (env `SECURITY_AUDIT_LOG_PATH`) via `<springProperty>`, default `/var/log/sessao-a-dois/security-audit.log` in `application.properties` (production; `docker-compose-prod.yml` bind-mounts this exact container path from a VPS directory, see `docs/DEPLOY.md`). **`api/src/test/resources/application.properties` overrides this to `target/test-logs/security-audit.log`** — without that override, `security.audit`-emitting tests would try to write to `/var/log` on the test host/CI runner, which usually isn't writable without root; this is a case where a property needs test-side mirroring even though no eagerly-instantiated Spring bean consumes it directly (Logback's `springProperty` resolves it from the Environment at logging-context init time, same class of gotcha as the `app.jwt.*`/`app.auth.*` mirroring rule above, just triggered by Logback instead of a `@Value` constructor arg). `RollingFileAppender` creates missing parent directories on first write, so running locally without `/var/log/sessao-a-dois` mounted does not break startup.

## Build / verify
- `./mvnw -DskipTests package` to compile; `./mvnw test` to run tests. **Both actually run in the devcontainer — use them.**
- The devcontainer ships Temurin JDK 21 + Maven 3.9.16 (`.devcontainer/Dockerfile`), and `.devcontainer/init-firewall.sh` allowlists `repo.maven.apache.org`/`repo1.maven.org`. This was added on 2026-08-02 precisely because the Flyway epic shipped 7 unverified stories and needed 5 manual fix commits afterwards — including a missing `spring-boot-flyway` dependency that a single `./mvnw compile` would have caught. **Never claim a backend change is done without running `./mvnw test`.** If it fails with a network error, re-run `sudo /usr/local/bin/init-firewall.sh` (Maven Central is behind a CDN with rotating IPs) before concluding anything.
- Still absent from the sandbox: `docker` and `psql`. Testcontainers and a real PostgreSQL are not available — which is exactly why the test datasource is H2 in `MODE=PostgreSQL` (see the Schema/Flyway note above). CI (`.github/workflows/`) runs against a real Postgres 17, so a migration that passes locally can still fail there on Postgres-only syntax.

## Docker
- `Dockerfile` is multi-stage: build (`eclipse-temurin:21-jdk`, uses `./mvnw`) → runtime (`eclipse-temurin:21-jre`, carries only the jar). Build with `docker build -t sessao-api ./api`.
- Layer-cache order matters: copy `.mvn/`, `mvnw`, `pom.xml` and run `dependency:go-offline` **before** `COPY src/`.
- Runtime copies `target/*.jar` → `app.jar`; the glob intentionally excludes the plugin's `.jar.original`. Keep `target/` in `.dockerignore`.
- The app needs a reachable datasource to boot (JPA auto-config), so `docker run` requires `DB_URL` pointing at an accessible PostgreSQL.
