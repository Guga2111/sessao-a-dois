- **Learnings for future iterations:**
  - Followed the MatchLike convention: recipientUserId/actorUserId are plain UUID @Column fields (conceptually FK to User), not @ManyToOne relations to User — only Couple gets a real @ManyToOne. Reuse this for any future notification-related entity.
  - Avoided naming a column `read` (SQL ambiguous/reserved-ish keyword) — mapped the boolean field `read`/`isRead()` to column `is_read` instead. If a future story queries this column directly (native SQL or a raw @Query string), remember it's `is_read` on the DB side.
  - Composite index for the "list unread notifications for a user" access pattern is declared via `@Table(indexes = @Index(columnList = "recipient_user_id, is_read"))` on the entity, consistent with how MatchLike/MediaTrack express table-level constraints in this codebase (e.g. MatchLike's @UniqueConstraint).
  - This sandbox has no JDK/Maven available (`mvn`/`java` not found, and `./mvnw` cannot download the wrapper because Maven Central is unreachable) — could not run `./mvnw test`/`package` to verify. Code was written to mirror MatchLikeRepositoryTest/MatchLike exactly (same annotations, same @DataJpaTest + CoupleRepository helper pattern) to minimize risk. Future iterations in this sandbox will hit the same limitation — verify on a machine with JDK 21 + Maven Central access before merging if this matters.
